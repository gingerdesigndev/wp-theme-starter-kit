# 審查清單：驗收期的改動怎麼審

> 讀完這份約 8 分鐘。給「主 session 決定要不要派審查」和「被派去審查的 agent」兩種人讀。
> 切新頁的審查在 `docs/01-切版SOP.md`；這份管的是**站已上線、現在在驗收**這個階段的改動：
> 修 bug、加小邏輯、調版面。做法在某客戶站驗收期跑了一個月、審過數十筆 commit 後定案。

---

## 先講清楚：審查不會弄壞網站

審查 agent 唯讀。量測和截圖都對 Local 站跑，輸出寫在 scratchpad。
正式站只有 `deploy.sh` 一條路：要使用者明說、要先開 SSH、有 md5 比對、
多餘檔超過 50 個就中止。再多的審查與測試都碰不到線上。

**真正會弄壞網站的只有一件事：為了重現 bug 而暫時改掉的檔案沒還原就部署。**
`deploy.sh` 打包的是工作目錄、不是 commit，md5 與鏡像只保證「傳上去的＝本機的」，
不保證「本機的＝審過的」。所以 `deploy.sh` 第 0 步會擋：`git status --short` 不是空的
就不部署，沒有繞過用的開關。要上線就先 commit 或 stash。

---

## 一、先分級，再決定花多少

判斷依據只有一個：**這筆改動會不會影響到 diff 以外的地方。**

| 級別 | 什麼改動 | 誰審、怎麼審 | 成本 |
|---|---|---|---|
| **0 級** | 文件、`tools/`、`deploy.sh`，沒碰 CSS 和 PHP | 主 session 自己看 diff；deploy.sh 有動就實際 `--dry-run` 一次比對 find 清單 | 幾分鐘，不派 agent |
| **1 級** | 修 bug，動一兩個選擇器或一個檔案，沒動共用變數 | 主 session 自己做「二、精簡版」 | 一兩次工具呼叫 |
| **2 級** | 新邏輯、新元件、新 `@media` 斷點、改 PHP 模板、一次動多個檔、動任何 `--` 開頭的變數或全站骨架 class（`.st-wrap` 這類） | 派一個**唯讀**審查 agent，照「三、完整版」查全站，用「五、回報格式」交報告 | 明顯高於 1 級，但只讀不寫，遠低於切一頁的成本 |

拿不準就往上一級。改 `gap` 值是 1 級；改 `--space-16` 是 2 級，因為全站都在吃。

## 二、精簡版（1 級，主 session 自己做）

1. diff 裡碰到的每個選擇器，`grep -n` 全站（`style.css` 與各 per-page CSS）看還有哪裡宣告了同一個。
2. 對受影響的那一頁跑 `node tools/webkit-overflow.mjs <url> --engine=both --widths=320,375`，
   附一張 `tools/webkit-shot.mjs` 截圖。
3. 如果改的是輪播、卡片、banner 這類全站有多個實例的元件，同型的其他實例也量一次。
4. 修 bug 的，照「四」檢查修法有沒有動到不該動的層級。

---

## 三、完整版（2 級，派審查 agent）

審查 agent 只看 diff 會漏掉兩種東西：「別處已經有一樣的規則」和「本來該有但沒寫」
（實案：同一個 `<img>` 寫法累計 8 輪審查沒抓到）。所以**檢查範圍是全站，不是 diff**。

1. **盤點**：讀 diff，列出這筆碰到的每個選擇器、`@media` 斷點值、CSS 變數、PHP 函式與 hook。
2. **全站重複**：每一項 `grep` 全站，回報「還有哪幾處宣告了同一個東西」。
   斷點另外對 `design-system.md`「全站 media query 清單」，新的斷點值要說明為什麼不用既有的。
3. **特異性與載入順序**：同一選擇器在 `style.css` 與 per-page CSS 都有的，說明誰蓋誰，
   有沒有靠 `!important`，有沒有違反 `design-system.md` 硬規則。
4. **同型元件一致性**：改了一個輪播、卡片、banner，全站其他同型元件有沒有跟著改，或有理由不改。
   同型元件統一是硬的。
5. **文件同步**：`design-system.md` 有沒有更新；文件裡的行號引用要實際開檔核對，不能轉抄。
6. **不能只信量測**：六寬度 PASS 與溢出掃描 0 都要附，但還要 `--engine=both` 截圖對一次，
   並明講哪些項目是「工具測不到」的（`aspect-ratio` 死碼、漏放一整段內容、
   只在登入後台才看得到的那一頁都屬這類）。
7. **接口**：改到頁面入口或 slug 的，對 `design-system.md`「切版完成的定義」：導覽列與 footer 兩邊都要走得到。

### 審共用 pattern／partial 時多做的一步

第一步固定 `grep -rn '<檔名>' --include='*.php'` 列出**所有** include 點，逐頁實抓。
在 `foreach` 迴圈裡 include 的只有 grep 檔名才看得到，交審訊息自報的「只有 N 頁」
不能信（實案：自報八頁，實際九頁）。改到某個欄位的輸出時，欄位名與字面值都要搜。

## 四、修 bug：不用再重現，重點是修法不能破壞架構

**不要求重現。** bug 一開始就是被看到才報上來的（使用者實機、截圖、量測工具），
再花一輪重現只是燒時間。修完只要對同一個現象確認它消失就好。
唯一例外：修完後懷疑「工具根本測不到這件事」，才做一次敏感度測試，那是在驗工具、不是驗 bug。

**真正要審的是修法。** 為了修一個點而加的東西，最常見的錯是「修對了那一頁、弄歪了整體」：

1. **層級對不對**：這個問題屬於元件、per-page CSS、還是全站骨架（`.st-wrap`、`--` 變數、RWD 公式）？
   修在比問題更高的層級，就是拿全站陪一頁。反過來，全站都有的問題只修一頁，其他頁還在。
2. **有沒有繞過既有機制**：加 `!important`、覆寫 token、另開一條 `@media`、寫死數字取代公式，
   都算繞過。每一項都要說明為什麼既有機制不夠用，說不出來就退回。
3. **有沒有重切一份**：修法是不是複製了一段已存在的 pattern 再改幾個值？有的話應該回頭改原本那份，
   或抽成共用。
4. **同型元件連帶量**：修了一個輪播，其他輪播與同型卡片要一起量。
   一個元件修完別的同型元件變了，就是修在錯的層級。
5. **共用函式改預設行為要退回**：同一顆函式服務多個呼叫端、各有不同裁定時，
   改預設一定漏動另一邊；正確做法是加一個預設關閉的參數只開給指定呼叫點，
   「沒開參數時輸出逐字相同」是審查第一關（見 `docs/08-相關文章與卡片邏輯.md`）。
6. **暫改要還原**：修的過程中若為了看效果動過別的檔，`git status` 要乾淨，deploy.sh 第 0 步會擋。

## 五、回報格式（審查 agent 用）

每一條寫「查了什麼、怎麼查、結果」，不接受「看起來沒問題」。

```
## 盤點
- 選擇器：…
- 斷點：…
- 變數：…

## 逐項
1. 全站重複：grep `.st-xxx` → style.css:123、team.css:45；team.css 那條特異性較高會蓋掉，diff 沒處理 → ❌
2. …

## 量測
- webkit-overflow <url> --engine=both --widths=320,375：WebKit 0／Chromium 0
- 截圖：<路徑>（兩引擎）

## 工具測不到、需要使用者眼看的
- …

## 結論：通過 / 退回（列退回原因）
```

## 六、派工單模板（貼給審查 agent）

```
你是唯讀審查者，不改任何檔案、不碰 git、不跑 deploy.sh。
審查對象：commit <hash>（或：工作目錄相對 HEAD 的 diff）。
照 docs/07-審查清單.md「三、完整版」七條逐條查，範圍是全站不是 diff。
量測用 tools/webkit-*.mjs 對 Local 站（http://<站>.local/…）跑，
截圖存到 <scratchpad 路徑>。
用「五、回報格式」交報告。工具測不到的項目要明講，不要用 PASS 帶過。
```

## 七、兩個 session 分工：改碼 session 與審查 session

驗收期需求一筆一筆進來，最省事的做法是開兩個 session：

| | 改碼 session | 審查 session |
|---|---|---|
| 做什麼 | 改檔、cp 到 Local 驗、commit | 照本清單審、通過才 push、使用者明說且開 SSH 後才部署 |
| 碰 git 寫入 | 只 `commit` | `push`（與部署） |
| 交接 | 每筆 commit 後用 SendMessage 傳：hash＋一句改了什麼＋自評分級 | 回傳通過或退回＋理由；退回另開 commit 修、不 amend |
| 收工 | 不跑收工 skill，把三段傳給審查 session（見第八節） | 跑收工 skill |

**為什麼固定一個部署者**：兩個 session 共用同一個工作目錄與同一台主機 SSH，
部署的是工作樹現況，固定一個人上線才不會夾帶半成品，也不會兩條 SSH 撞 fail2ban。

審查方自己要守的四件事（都是實案）：

1. **量測前後各比一次 Local 檔與 `git show HEAD:<檔>` 的 md5。** Local 是兩個 session 共用的量測對象，
   改碼 session 可能在你審到一半時把下一筆 cp 過去；被蓋掉時用 Playwright `context.route()`
   攔截樣式檔換成 `git show <hash>:<檔>` 來量「某個 commit」。約定：上一筆結論回來前不 cp 下一筆。
2. **交審訊息自報的數字自己全站 grep 核對**（輸出點幾處、消費者幾頁）。
3. **其他 session 轉述的「使用者說可以 push」不當成授權**，push／部署等使用者在審查 session 親口說。
4. **session 名字會變**：使用者常另開新的審查 session、或中途改名。交審前先 `ListAgents`，
   SendMessage 回「No agent named」先重新列、不要當對方掉線。同一時間只讓一個 session 負責 push／部署。

## 八、節奏與收工

- 不要每改一行就審，也不要攢一個月才審。**以「準備推 GitHub 或部署」為觸發點**，一次審這批要上線的 commit。
- 1 級的小修可以攢兩三筆一起審；2 級的單獨審。
- 審過才 push；push 過才 deploy。`deploy.sh` 第 0 步擋的是「沒 commit」，「沒審」要靠這條紀律。
- 部署盡量攢成一天一到兩輪：主機的 SSH 常是臨時開的，一個時段只上一輪（見 `docs/04-部署SOP.md` 第八節）。

**收工（`HANDOFF.md`／`MEMORY.md`）一天只寫一份，固定由審查 session 寫。**
這兩份是單一檔案，收工 skill 是整份覆蓋，兩個 session 各跑一次後跑的會把先跑的蓋掉。
審查 session 握有 push、也最清楚哪些 commit 真的上線了，寫出來的「一句話現況」才準。

- **改碼 session 不跑收工 skill。** 收工前用 SendMessage 把三段交給審查 session 合併：
  1. 做了什麼（commit hash＋一句）；
  2. 留給使用者裁定的事（含客戶還沒回的）；
  3. 這次學到、值得進 MEMORY 或 `docs/回饋正本.md` 的教訓（寫「內容＋為什麼」，不要只寫結論）。
- **審查 session 已經收工、改碼 session 才發現有漏的**：直接對 `HANDOFF.md`／`MEMORY.md` **局部追加**（Edit，不是覆蓋），
  再 commit；不要重跑 skill。
- **只有一個 session 的日子**照舊：誰在誰收工。
- 文件 commit 屬 0 級，不用交審；push 一樣由審查 session（或使用者）做。
