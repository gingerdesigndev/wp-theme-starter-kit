# ACF 規範

> 讀完這份約 8 分鐘。這份講的是「客戶能自己改的內容」怎麼接、怎麼存、怎麼驗——
> 不是 ACF 的操作教學，是這套起案包對 ACF 的用法規範。
>
> AI 這邊沒有對應的 skill；這份文件本身就是規範來源，改 ACF 相關程式碼前先讀這份。

---

## 一、三層分離（這是全篇主軸）

「客戶要能自己改的內容」用 ACF PRO 接。但**「ACF 欄位」這件事其實拆成三層**，
各自存在不同地方，進不進 git 也不一樣：

| 層 | 是什麼 | 存哪 | 進 git 嗎 |
|---|---|---|---|
| 設定頁的「存在」 | 後台要不要有「網站設定」這個選項頁面 | `functions.php`（PHP 註冊，`acf_add_options_page()`） | ✅ |
| 欄位「定義」 | 這個設定頁底下有哪些欄位、叫什麼名字、什麼型態 | `acf-json/`（ACF 存檔時自動同步出的 JSON） | ✅ |
| 欄位「值」 | 客戶實際填了什麼字、傳了什麼圖 | 各站自己的 `wp_options` 資料表 | ❌ |

**為什麼設定頁要用 PHP 註冊、不在後台點一點就好：**

後台手動建立的設定頁面，其「存在」這件事本身是存在資料庫裡的（跟一般文章一樣存
`wp_posts`）。換一個環境（例如從 Local 搬到正式站、或正式站砍掉重建），資料庫是
空的，後台點出來的東西不會跟著搬過去——得在新環境重新點一次。

用 PHP 註冊（`functions.php` 裡的 `add_action('acf/init', ...)`）就不會有這個問題：
設定頁的「存在」變成程式碼的一部分，跟著主題一起進 git、一起部署，換環境自動就有，
不需要人工在後台重建一次。

這支起案包目前唯一的設定頁是 `site-options`（後台顯示「網站設定」），註冊在
`functions.php` 的「4) ACF：註冊「網站設定」設定頁」段落。新站如果要加第二個設定頁
（例如「首頁設定」「聯絡資訊」），照同樣的模式在 `functions.php` 裡加一段
`acf_add_options_page()`，不要在後台點新增。

**欄位定義為什麼要進 `acf-json/`：**

`functions.php` 只管「設定頁存不存在」，不管「這個設定頁底下有哪些欄位」。欄位本身
（叫什麼名字、什麼型態、有幾個、順序、說明文字……）是在後台 ACF 介面裡編輯的，但
ACF 有一個機制：只要主題根目錄有 `acf-json/` 且可寫，**每次在後台存檔欄位群組，ACF
就會自動把整個群組匯出成一份 JSON**，存進 `acf-json/`。這個自動同步是
`functions.php` 的「5) 讓 ACF 欄位群組自動存進 acf-json/」段落掛的兩個 filter
（`acf/settings/save_json`、`acf/settings/load_json`）啟用的。

因為有這層自動同步，**欄位定義也不需要手動在新環境重建**——只要 `acf-json/*.json`
跟著主題一起進 git、一起部署，新環境的 ACF 開機時會自動讀 `acf-json/` 把欄位群組
「還原」出來，後台會直接看到欄位，不需要重新設定一次。

**欄位「值」則完全相反，永遠不會、也不應該進 git：**

值是客戶實際填的內容（電話、地址、Hero 文案、上傳的圖……），是各站自己的資料，
不是主題骨架的一部分。它存在該站自己的 `wp_options` 資料表裡，命名規則是
`options_<欄位名>`（見第四節）。這也代表：**每個新環境部署上去之後，這些值一開始
一律是空的**，得由客戶（或你）到後台重新填一次。這不是 bug，是這套三層分離設計的
必然結果——正是第三節要講的陷阱。

## 二、安全讀值紀律：一律走 `st_opt()`

版型檔（`front-page.php`、`header.php`、`footer.php`、`template-parts/*.php` 等）
讀「網站設定」的值時，**一律呼叫 `st_opt()`，不要直接呼叫 `get_field()`**。

`st_opt()` 定義在 `functions.php`：

```php
if (!function_exists('st_opt')) {
    function st_opt($name, $fallback = '') {
        if (!function_exists('get_field')) return $fallback;
        $value = get_field($name, 'option');
        return ($value === null || $value === false || $value === '') ? $fallback : $value;
    }
}
```

它包了兩層保險，各自防不同的事：

**第一層：`!function_exists('get_field')` 防的是「ACF 被停用」。**

`get_field()` 這支函式是 ACF 外掛提供的，主題本身不帶。如果哪天 ACF 外掛被停用、
過期停用、或客戶不小心點掉了，`get_field()` 這個函式根本不存在——版型檔如果直接
呼叫它，PHP 會丟 `Fatal error: Uncaught Error: Call to undefined function`，**整站
白畫面**。客戶站上裝的外掛不是我們能完全控制的，這層保險必須有，不能省。

**第二層：值為空時回退 `$fallback`，防的是「新環境還沒填值」。**

承第一節，欄位「值」不進 git，每個新環境部署上去都是空的。如果版型檔沒有回退機制，
新站起案完、部署上去、客戶還沒進後台填值之前，前台會是一片空白（Hero 標題空的、
電話空的……）。`st_opt()` 的第二個參數就是這種情況的回退值——通常是接欄位前的
硬編示範文字，或乾脆是空字串讓那個區塊判斷不輸出。

**兩層保險防的是完全不同的兩種故障**：第一層防的是「外掛層級的意外」（ACF 消失），
第二層防的是「資料層級的常態」（新環境沒填值，這不是意外，是每次起案都會發生的
正常狀態）。兩層都要有，缺一層都會在不同情境下讓前台掛掉或開天窗。

## 三、回退值的陷阱：回退值 = 真實值時，看前台無法證明欄位接通了

這是接 ACF 欄位時最容易誤判「成功」的一個坑，務必記住。

`st_opt('hero_title', '歡迎光臨')` 這種寫法很常見：欄位還沒接上示範資料時，
`$fallback` 常常就直接寫接欄位前原本的硬編文字。這時候會出現一個陷阱——

**如果 ACF 欄位值剛好也填成跟 `$fallback` 一樣的字**，那麼：

- 欄位真的接通了、`get_field()` 讀到值 → 前台顯示這段文字
- 欄位完全沒接通、一路走 `$fallback` 回退（例如欄位名打錯、ACF 沒啟用、
  `location` 規則設錯欄位群組根本沒出現在這個設定頁）→ 前台**也**顯示這段文字

**兩種情況輸出一模一樣**，光看前台正常沒辦法分辨「欄位真的接通了」還是
「完全沒接通、純粹靠回退值撐著」。這是 `st_opt()` 這種回退設計的固有盲點，不是
寫錯，是任何「有回退值」的讀值函式都會有這個問題。

**可靠的驗法：清空值再看一次，確認前台確實變了。**

具體做法：

1. 到後台把該欄位的值改成別的字（或清空、或改成一眼能認出的測試字串，例如
   `TEST-123`）並存檔。
2. 重新整理前台頁面。
3. 前台文字如果**跟著變成**你改的內容 → 欄位真的接通了。
4. 前台文字如果**還是原本那段**（沒變成 `TEST-123`）→ 欄位沒接通，回頭檢查
   欄位名稱是否對得上 `st_opt()` 呼叫時傳的 `$name`、ACF 欄位群組的 `location`
   規則是否真的指到這個設定頁（`options_page == site-options`）、以及 opcache
   是否餵了舊碼（見 `docs/05-踩坑清單.md`）。

測完記得把值改回正確內容——這個驗法本身會短暫改到真實內容，跟部署 SOP 提到的
土法驗證是同一類手法。

## 四、欄位命名不可事後改

ACF 欄位的值存進 `wp_options` 時，`option_name` 是以**欄位名稱（`name`，不是
`label`）** 組出來的，格式是 `options_<欄位名>`。例如 `site_logo` 這個欄位的值存在
`wp_options` 的 `options_site_logo` 這一列。

**一旦這個欄位有人填過值，就不要再改欄位名稱（`name`）。**

原因：改名之後，ACF 讀值時會去讀 `options_<新名字>`，但資料庫裡真正有值的那一列
還叫 `options_<舊名字>`——等於新名字讀到的是空的，舊名字底下的舊值變成沒有任何
欄位定義指向的孤兒資料，永久留在資料庫裡沒人讀得到，也不會自動被清掉。這對客戶
來說看起來就是「我明明填過的內容，怎麼突然不見了」。

**要改的是顯示名稱，不是欄位名稱：**

- 想調整後台看到的字（例如「聯絡電話」想改成「診所電話」）→ 改 **label**，
  這個只影響後台 UI 顯示，不影響存值位置，可以隨時改。
- **name**（例如 `contact_tel`）→ 一旦上線填過值，視同鎖定，不要改。

真的需要重新命名時（例如欄位名一開始就取錯、還沒上線填值），確認方式是查
`wp_options`：

```sql
SELECT option_name, option_value FROM wp_options WHERE option_name = 'options_<欄位名>';
```

查不到任何列，代表這個名字底下還沒有值，這時候改名是安全的；查得到，就不要動
`name`，只能改 `label`。

## 五、ACF 授權：席次怎麼算，開新站前先確認夠不夠

ACF PRO 是授權制，同時能使用的「站」數量有上限（席次）。**環境是不是佔席次，是
授權伺服器依網址樣式在伺服器端判定的**，外掛本機端沒有判斷邏輯、也沒有設定或
filter 能覆蓋這個判定。

一般認知裡「開發環境」「測試環境」不佔席次，但這條界線**不是由你決定的，是網址
長什麼樣決定的**。常見不佔席次的網址樣式：`localhost`、IP、`.local` / `.loc` /
`.localhost` / `.test` 這類本機開發網域、`test.` `testing.` `sandbox.` `dev.`
`local.` 這類前綴、`stage.` `staging.` 這類前綴，以及主流主機商（如 WP Engine、
Kinsta、Flywheel）自帶的暫存網域。**其餘一律算 production，佔一個席次。**

實務上要注意兩件事：

1. **開新站前先確認席次還夠。** 每接一個新客戶站，只要它的正式網址不落在上面
   那些「不佔席次」的樣式裡，就會吃掉一個席次。手上同時維護的站數量逼近授權
   上限時，先確認要不要加購，不要等到新站上線才發現卡住。
2. **未來要給客戶開雲端預覽站，網址要取成 `staging.<正式域名>` 或
   `dev.<正式域名>`**，才會落在「不佔席次」的樣式裡。如果隨便取一個獨立網域
   （例如 `xxx-preview.com`），會白白多吃一個席次。
3. **解約、下架某個站時，記得把席次收回來**（到 ACF 帳號管理頁面移除該站），
   不要放著不管——這件事的成本要算進報價：如果客戶解約但你忘記收回席次，
   等於用自己的授權額度養一個已經不再收費的站，直到席次滿了才會發現。

授權過期不會讓已上線的站當機：前台照常運作，既有的 PRO 型態欄位（image、
repeater 這類）也照常能編輯。但會失去兩件事：**不能再新建 PRO 型態的欄位**、
**收不到外掛更新**。後者放久了會累積 WordPress / PHP 版本相容性風險，不是
「反正能用就不用管」。

## 六、新站怎麼建欄位群組

新站起案後，需要在 ACF 後台建立新的欄位群組（或在既有的「網站設定」群組裡加欄位）
時，照以下步驟：

1. 後台 → **ACF** → **欄位群組** → **新增**。
2. 加完需要的欄位（型態、名稱、說明文字視需求設定；名稱一旦上線填值就不能改，
   見第四節）。
3. **位置規則**（Location Rules）設成：`選項頁面` **等於** `網站設定`
   （對應 `functions.php` 裡 `menu_slug` 設的 `site-options`）。這一步決定了
   這個欄位群組會出現在哪個設定頁底下，設錯會導致欄位群組完全不出現、
   或出現在錯的地方。
4. 存檔。存檔的當下，`acf-json/` 目錄底下會**自動**出現（或更新）對應的 JSON
   檔案——這是 `functions.php` 第五段掛的 `acf/settings/save_json` filter 在做
   的事，不需要手動匯出。
5. **記得 `git add acf-json/*.json` 並 commit。** 這一步最容易漏——`acf-json/`
   是自動同步沒錯，但「同步進本機檔案系統」跟「進 git」是兩件事，前者是 ACF
   做的，後者要靠人（或 AI）記得把它加進版本控制。漏掉這步，欄位定義只存在
   你自己電腦的檔案系統上，部署到正式站、或換一台電腦開發，欄位群組都不會出現。

## 附：現有欄位群組對照（`acf-json/group_site_options.json`）

目前起案包內建一組示範欄位群組，設定頁 slug 為 `site-options`（後台顯示
「網站設定」），底下十個欄位：

| 欄位名（`name`） | 型態 | 用途 |
|---|---|---|
| `site_logo` | image | 網站 Logo；空值時 header 退回顯示站名文字 |
| `contact_tel` | text | 聯絡電話；空值時 footer 聯絡資訊區整區不顯示 |
| `contact_address` | text | 地址；空值時 footer 聯絡資訊區整區不顯示 |
| `hero_title` | text | Hero 標題；必填才會顯示整個 Hero 區 |
| `hero_subtitle` | textarea | Hero 副標；選填 |
| `hero_image` | image | Hero 底圖；選填 |
| `hero_cta_text` | text | Hero 按鈕文字；要與 `hero_cta_url` 一起填才顯示按鈕 |
| `hero_cta_url` | url | Hero 按鈕連結；要與 `hero_cta_text` 一起填才顯示按鈕 |
| `cards_heading` | text | 卡片區標題；選填 |
| `cards` | repeater | 卡片區內容，子欄位 `title` / `body` / `image`；`title` 留空的列不輸出（見 `functions.php` 的 `st_has_cards()`） |

這組欄位的值全部以 `options_<欄位名>` 存在 `wp_options`，例如電話存在
`options_contact_tel`。新站要加欄位、或改示範內容，照第六節的步驟在後台操作，
不要直接手改 `acf-json/group_site_options.json` 的 JSON 檔——手改容易漏欄位屬性
（`key`、`type` 的搭配參數等），且下次在後台存檔時會被 ACF 用後台當下的狀態覆蓋。
