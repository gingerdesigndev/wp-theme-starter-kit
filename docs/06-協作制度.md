# 協作制度

> 讀完這份約 5 分鐘。目的是讓你知道：AI 在這個專案能做什麼、不能做什麼、
> 你必須親手做什麼、憑證要放哪裡，以及**什麼時候不該直接相信它的結論**。
>
> 技術細節在專案自己的 `MEMORY.md`（長期事實）、`HANDOFF.md`（目前進度）；
> 這份只談協作方式本身，不是技術文件。

---

## 一、分工表：誰能做什麼

| 工作 | AI | 你 | 說明 |
|---|:---:|:---:|---|
| 改主題碼（PHP／CSS／模板） | ✅ | ✅ | |
| 部署到正式站 | ✅ | ✅ | `./deploy.sh`，見 `docs/04-部署SOP.md` |
| 建頁面／改選單／改設定 | ✅ | ✅ | AI 走 REST API，需要 Application Password |
| 查主題清單、驗證部署結果 | ✅ | ✅ | |
| **啟用／切換主題** | ❌ | ✅ | WP 核心的 REST API **沒有這個端點**，只能後台手動按 |
| **把 SSH 公鑰裝到主機** | ❌ | ✅ | 這一步要輸入主機登入密碼，AI 不碰密碼 |
| **給 AI 你的帳號登入密碼** | ❌ | ❌ | **不要做。** 見下一節為什麼 |

「AI 不能啟用主題」不是刻意設下的限制，是 WordPress 核心 REST API 本來就沒有提供
切換啟用主題的端點——就算想自動化也做不到，只能人工到後台按。「AI 不碰你的登入
密碼」則是刻意的邊界，見下一節。

---

## 二、兩條獨立權限管道

**這是整個協作的基礎概念。搞混它，後面每件事都會卡。**

AI 對這個站的存取，分成兩條完全獨立、互不影響的管道：

| 管道 | 憑證放哪 | AI 能碰 | AI 碰不到 |
|---|---|---|---|
| **SSH** | `~/.ssh/<專案>.key`（私鑰只在你自己電腦上） | **檔案**：主題原始碼、部署 | 資料庫、內容、設定 |
| **REST API** | `<專案根>/.env`（Application Password） | **內容／設定**：頁面、選單、欄位值 | 檔案系統 |

**兩條互不影響**：撤銷 Application Password，`./deploy.sh` 照跑不受影響；SSH 斷了，
REST API 一樣能用。這個獨立性是刻意設計的——任何一條出問題，不會連帶讓另一條也失效，
你可以只針對出問題的那一條處理，不用整組憑證一起重來。

### SSH：AI 產金鑰，你自己裝上去

```bash
# ⚠️ 在「你自己的電腦」上跑，不是先 SSH 進伺服器之後再跑！
ssh-copy-id -i ~/.ssh/<專案>.key.pub -p <PORT> <USER>@<HOST>
```

`ssh-copy-id` 需要輸入主機的登入密碼，這一步只有你能做。AI 產生金鑰對、把公鑰交給
你之後，剩下的動作它插不上手，也不該插手。

**撤銷**：從主機的 `authorized_keys` 移除對應公鑰，或直接停用/刪除那把金鑰。

### REST API：跟 AI 說一句話，它會引導你走完

直接跟 AI 說：**「我授權你操作後台權限，請你協助我產生 Application Password /
.env 檔案」**，它會引導你走完整個流程並驗證結果。

分工是這樣（**下面這兩件事只有你能做**）：

1. **產生密碼**：WP 後台 → 使用者 → 個人資料 → 應用程式密碼 → 命名 → 產生 → 複製
   （只顯示這一次，關掉頁面就看不到了）。AI 沒有登入權，這步它做不到；而且 REST API
   雖然有建立 Application Password 的端點，但呼叫那個端點本身就需要先有憑證——
   雞生蛋的問題，只能人工在後台產生第一組。
2. **把值填進 `.env` 並自己執行**（**不要把密碼貼在對話框裡**，那會讓它明文留在
   對話紀錄裡）：

```bash
cat > <專案根>/.env <<'EOF'
SITE_WP_URL='https://example.com'
SITE_WP_USER='帳號'
SITE_WP_APP_PASSWORD='xxxx xxxx xxxx xxxx xxxx xxxx'
EOF
chmod 600 <專案根>/.env
```

> **值一定要用單引號包住。** Application Password 的格式含空格（例如
> `xxxx xxxx xxxx xxxx xxxx xxxx`），沒有引號的話 shell 會把它拆成好幾個獨立的詞、
> 只取第一段當作變數值，其餘部分被當成獨立指令或直接丟失，整個變數會變成不完整
> 或空白的值——而且這種失敗通常沒有明顯的錯誤訊息，會在之後呼叫 API 時才用「認證
> 失敗」的方式間接暴露出來，不容易第一時間聯想到問題出在引號漏加。

AI 負責的部分：把上面這段指令準備好給你、確認 `.env` 的格式與檔案權限正確、
測試認證是否成功、之後從檔案讀取憑證使用——它不會、也不能自己產生或看到密碼本身。

**撤銷**：後台「應用程式密碼」清單裡一鍵刪除對應項目，不影響你自己的帳號登入。

## 三、不可逆動作先確認

部署、啟用主題、覆蓋客戶檔案、對外發佈——這類一旦做了很難簡單復原的動作，AI 應該
**先列出「即將發生什麼」，等你明確點頭再做**，不要自己判斷「應該沒問題」就直接執行。

**這不是效率低落，是設計。** 不要因為想快而叫它跳過這一步——它停下來問的時候，
通常是有理由的。

**真實案例**：某個客戶站遷移專案，第一次要把新主題部署到正式站時，AI **拒絕直接
上傳**，並且指出「現在上正式站會弄壞線上官網，因為只有首頁完成遷移、其餘頁面還
依賴舊的頁面建構器」。事後確認**這個判斷是對的**。這個「先確認」的機制在那次真的
攔下了一次會造成實際損害的操作，不是空跑流程。

（同一個專案還另外記錄過一條獨立的硬依賴：遷移還沒做完就先停用舊的頁面建構器，
會讓其餘尚未遷移的頁面同時故障。這是兩件各自成立的觀察，不是同一次事件的兩個
環節，這裡刻意不把兩者接成一句因果敘事——完整依賴順序見 `docs/00-開站六步.md`
「分支 A：遷移既有站」。）

## 四、什麼時候不該相信 AI

AI 的判斷不是永遠可靠，以下兩個真實案例值得記住——不是要你凡事都懷疑，而是知道
「在哪些情境下，AI 給出的結論特別值得你自己再確認一次」。

### 案例一：用錯觀測工具，得到錯的結論，追了一整輪

AI 用 headless（無頭）瀏覽器截圖判斷版面有沒有問題，看到頁面 header 消失，
先後宣稱是「CSS 寫錯」、又改口是「opcache 沒清」——**兩個結論都錯**。真相是：
那個版面用了滿版（`width:100vw`）的元素，這類元素在某些 headless 瀏覽器的算繪
環境下會出現渲染異常（依視窗高度而不是寬度出錯），把畫面上半部吃掉；**真實瀏覽器
對同一份程式碼完全正常顯示**。

**教訓：AI 的結論只跟它使用的觀測工具一樣可靠。** 版面這類「眼見為憑」的問題，
自己開一次真實瀏覽器看一眼，比它連續截十張自動化截圖分析半天更快找到真相。

### 案例二：人的堅持挖出了真問題——低風險 ≠ 高資訊

AI 建議「看後台的主題清單確認狀態就好，不需要真的啟用主題來測試」——這是它評估
下風險最低的驗證方式。使用者堅持「我還是想啟用看看」，**啟用之後才發現**：舊的
頁面建構器有一個「Theme Builder」功能，會整個蓋掉新主題的 header/footer。這個坑
如果沒有在這個階段被人為堅持測出來，會一路潛伏到整站正式遷移的當下才爆出來，而且
到那個階段已經很難聯想到問題出在這裡。

**教訓：AI 傾向選擇「風險最低」的驗證方式，但低風險不等於高資訊量。** 風險最低的
做法通常也是驗證強度最弱的做法——它確實不會把系統弄壞，但也因此測不出真正會在
更嚴苛情境下才出現的問題。你想多測一點、想親自動手驗一次，就去測，不需要因為
AI 說「這樣就夠了」而打消念頭。

## 五、HANDOFF / MEMORY 怎麼寫

兩份文件負責不同的事，職責分清楚才不會漂移：

| 文件 | 內容 | 生命週期 |
|---|---|---|
| **HANDOFF.md** | 這次工作做了什麼、改了哪些檔案、還有什麼沒做完、下次要從哪裡接 | 每次工作階段結束時更新，內容會被下一次的內容取代或大幅改寫 |
| **MEMORY.md** | 跨對話的長期事實與踩過的坑——不會隨著某一次工作結束就過期的東西 | 只增量附加，新項目附在檔案最後並標上日期，不刪改舊項目 |

**同一件事不要兩邊都寫。** 這條規則存在的理由是：兩份文件的更新頻率不同
（HANDOFF 幾乎每次工作階段都更新，MEMORY 只在學到新的長期教訓時才追加），如果
同一個事實兩邊都寫了一份，隨著時間推移，兩份的內容遲早會不一致——例如某個設定值
後來變了，HANDOFF 裡的那份被更新，但 MEMORY 裡那份沒人記得去改，之後有人讀到
MEMORY 版本的舊資訊，就會照著已經過期的內容行動。

**判斷該寫哪一份的簡單方法**：這件事「下一次工作階段結束後還重要嗎」——重要就寫
MEMORY，不重要（只是這次做到哪、下次接哪裡）就寫 HANDOFF。踩到的坑、學到的教訓、
影響全專案的長期決策，一律進 MEMORY；「這次改了哪五個檔案、還差哪一步沒做完」，
一律進 HANDOFF，不要讓 MEMORY 塞滿只有這一次工作階段才有意義的細節。
