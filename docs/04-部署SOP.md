# 部署 SOP

> 讀完這份約 5 分鐘。目的是讓 `./deploy.sh` 第一次跑起來不踩坑，
> 以及連不上時知道自己在跟哪一種問題打交道。
>
> 這份講的是「怎麼把改動送到正式主機」。開站之前的六個步驟見
> `docs/00-開站六步.md`；跑起來以後遇到的怪現象查 `docs/05-踩坑清單.md`。

---

## 一、前置：填設定、裝金鑰

### 1. 複製並填 `.deploy.env`

```bash
cp .deploy.env.example .deploy.env
```

打開 `.deploy.env`，把主機資訊填進五個欄位（`SITE_HOST`、`SITE_PORT`、`SITE_USER`、
`SITE_KEY`、`SITE_REMOTE_DIR`）。`.deploy.env` 已列入 `.gitignore`，**不會**被提交——
它含主機位址與金鑰路徑，這是刻意的隔離。

`deploy.sh` 不帶任何預設值。設定檔漏填一項就直接中止，不會用預設值「湊合跑起來」——
客戶站傳錯主機的代價太高，寧可停下來問，也不要用猜的值跑完一次部署。

### 2. 裝 SSH 金鑰

流程是：AI 產金鑰 → 給你公鑰 → **你自己**在自己的電腦上把公鑰裝上去。

```bash
# ⚠️ 在「你自己的電腦」上跑，不是先 SSH 進伺服器之後再跑！
ssh-copy-id -i ~/.ssh/<專案>.key.pub -p <PORT> <USER>@<HOST>
```

`ssh-copy-id` 要輸入主機的登入密碼，這一步只有你能做——AI 不碰密碼。裝好之後，
`.deploy.env` 的 `SITE_KEY` 指到同一支私鑰，`deploy.sh` 才連得上。

主機面板另外給的那組「使用者密碼」不要貼給 AI，金鑰是唯一該用的憑證。完整的權限模型
（SSH 與 Application Password 兩條管道分別碰得到什麼）見 `docs/06-協作制度.md`。

## 二、主機能力偵測：先測，別假設

不同主機的能力差很多——有的是完整 VPS，有的是精簡容器，連 `rsync`、`sftp-server`、
`php` CLI 都沒有，只留了 `tar` + `gzip`。**新站主機不一定跟上一個客戶站一樣**，
每次接新主機都先測一次：

```bash
ssh -i <KEY> -p <PORT> <USER>@<HOST> 'for c in rsync tar gzip php; do printf "%s: " "$c"; command -v $c || echo 無; done'
```

- **有 `rsync`**：可以用 rsync 增量同步，效率較好，但不是本起案包 `deploy.sh` 的預設路徑。
- **沒有 `rsync`**（實測過的客戶站環境常是這樣）：走 `deploy.sh` 內建的 **tar over SSH**——
  這是預設路徑，不需要額外設定，對「精簡容器」這種最常見的限制環境天生相容。

不要假設主機一定有 `rsync` 就照抄別的專案的部署腳本；也不要假設它一定沒有就永遠只用
tar。**先跑上面那行偵測指令再決定**，這行成本很低、能省掉一輪「部署腳本用了主機沒有
的工具，卡在中間才發現」的返工。

## 三、五層驗證：只做第一層不算數

`./deploy.sh` 把部署拆成五層，**任一層失敗就中止**，不會「跳過失敗的一層繼續做下一層」：

| 層 | 做什麼 | 為什麼不能省 |
|---|---|---|
| 1. 打包內容檢查 | 打包完先 `tar tzf` 檢查包裡有沒有夾帶不該上線的東西（`.git/`、內部文件、`.claude/`、`.superpowers/`） | 只確認「打包成功」不代表「打包的內容是對的」——這層專門抓「排除清單漏寫了什麼」 |
| 2. SSH 連線檢查 | 用金鑰跑一次最輕量的連線測試 | 連不上就不要往下走，見第四節的判定表 |
| 3. md5 比對 | 本機打包的 md5 跟上傳到主機後算出來的 md5 逐位元核對 | 傳輸中斷或截斷不會讓指令回報失敗，只有內容比對抓得到 |
| 4. 鏡像對齊 | 比對本機與遠端的完整檔案清單，把「遠端有、本機已經沒有」的檔案刪掉 | tar 解壓**不會刪除**遠端既有檔。本機刪掉的素材、曾經上傳後來排除掉的內部文件，不做這層會一直留在遠端，包括本來不該外流的檔案 |
| 5. 逐檔 diff | 鏡像對齊後，再拿本機清單跟遠端清單做一次完整 diff | 確認「本機有的，遠端也有；本機沒有的，遠端也沒有」，這是唯一能保證兩邊一致的做法 |

**只做第一層不算數**——很多失敗的部署看起來像是「打包成功了、上傳指令沒有報錯」，
但那只代表本機這邊沒出錯，不代表遠端真的收到了正確、完整的檔案。「指令沒有報錯」
和「部署真的成功」是兩件事，中間那三層驗證就是在補這個落差。

鏡像對齊有一道防呆：**多餘檔超過 50 個判定異常、直接中止、不亂刪**——這通常代表
`SITE_REMOTE_DIR` 設錯了（例如指到了別的專案的目錄），這時候寧可停下來人工確認，
也不要讓腳本自己猜著刪。

想在部署前先看看鏡像會刪什麼、不想真的送出，跑：

```bash
./deploy.sh --dry-run
```

**不要自己另外開一條 SSH 去 `find` 遠端清單來預覽**——這正是第四節要講的連線紀律
所警告的事：多開的每一條連線都算一次連線，都可能把你推向 fail2ban 的門檻。

## 四、連線紀律：連不上時不要重試

**SSH 連不上時最直覺的反應是「等一下再跑一次」——這是錯的，會把問題越搞越糟。**

多數主機都有類似 fail2ban 的機制：短時間內連線失敗次數過多會被暫時封鎖。**關鍵在於
每一次失敗的連線嘗試，本身就會把封鎖的倒數計時重新歸零**。所以「等 15 分鐘 → 跑一次
部署 → 又失敗 → 再等 15 分鐘」是一個永遠出不去的迴圈：你以為在等待封鎖解除，實際上
每次重跑都在延長封鎖。

`deploy.sh` 的「檢查金鑰連線」這一步會讀 SSH 回傳的原始錯誤，分類成三種情況分別給出
處置方式，不要看到連線失敗就統一當成「等一下」：

| 錯誤特徵 | 判定 | 處置 |
|---|---|---|
| `kex_exchange_identification`、`Connection reset`、`Connection closed by` | **封鎖生效中**（TCP 連得上、但一握手就被切斷） | 到主機面板把 SSH 服務**停止再啟動**——重啟能清掉封鎖狀態，等待不能。**不要重跑本腳本**，每次失敗都會延長封鎖 |
| `Permission denied`、`Too many authentication`、`Invalid key`、`no matching host key` | **金鑰問題**（連得上、但金鑰不被接受） | 確認金鑰檔存在、權限是 `600`、公鑰確實裝在主機上。這與連線封鎖無關，重啟 SSH 服務沒有幫助 |
| `Connection refused`、`Connection timed out`、`No route to host`、`Operation timed out` | **SSH 服務本身沒開，或網路不通** | 先用 `nc -z -w 8 <HOST> <PORT>` 測 TCP：不通就到主機面板把 SSH 服務啟動；通了但還是這個錯，回頭看上面兩種 |

有些主機（尤其是容器化、精簡型的主機）SSH 服務不是常駐的，可能會自己停掉；重啟後
連線資訊（主機名、埠號）也可能改變。**這代表「連不上」有相當比例根本不是防火牆或
金鑰問題，而是服務沒開**——先用上面的判定表分辨，再動作，不要憑直覺猜。

`--dry-run` 也會連一次 SSH（為了列出遠端清單做預覽），跟正式部署一樣受這條紀律約束：
它連線失敗一樣會讓封鎖倒數歸零，**不能因為它「只是預覽」就放心重跑**。

## 五、部署後：主題不會自動生效，快取不會自動清

`deploy.sh` 完成之後印出的成功訊息會提醒兩件容易漏掉的事：

1. **主題不會被自動啟用，這是刻意的設計。** 部署只上傳檔案，絕不碰資料庫、絕不切換
   啟用中的主題。啟用一律要人為到 WP 後台按——理由見 `docs/06-協作制度.md`「不可逆
   動作先確認」一節；WP 核心的 REST API 也確實沒有切換主題的端點，AI 就算想自動化
   也做不到。
2. **有頁面快取外掛時，改動 theme 檔不會自動觸發清快取。** 快取外掛（WP Rocket、
   LiteSpeed Cache、W3 Total Cache 這類）通常只認「內容被更新」（例如文章被重新儲存），
   不認「主題檔案被換掉」。部署完檔案已經是新的，但訪客看到的可能還是快取住的舊版
   HTML，直到快取被清除或過期。

   **驗證一定要用裸網址**：`curl https://example.com/`，**不要加任何 query string**。
   加 `?v=時間戳` 這類 cache-buster 確實能繞過快取拿到即時版本，但那證明的是「程式碼
   本身是對的」，不是「訪客現在看到的是對的」——這兩者是不同的問題，只驗前者會讓你
   誤以為部署完全成功，卻漏掉快取沒清這件事。

   多數快取外掛的清除是**逐頁**的：改一個會影響全站版型的東西（header、footer、選單）
   之後，重新儲存單一頁面通常只清那一頁的快取，其他已經被訪問過、已經被快取住的頁面
   仍然是舊版。**改動若影響全站版型，要逐頁抽驗，而且都要用裸網址**——只驗首頁就宣告
   「部署成功」，漏掉的是內頁還沒被清快取這件事。

## 六、HTTP 200 不等於成功

**`curl` 回傳 200 只代表伺服器有回應內容，不代表回應的內容是你想要的那個版本。**
至少三種情況會讓你在裸網址上看到 200，卻不是真正部署成功的證據：

- 頁面快取外掛餵的是**清快取之前的舊版 HTML**（見上一節）。
- 部署過程中如果主機正在重啟某個服務、或有中繼架構暫時異常，可能會由中間層（路由器、
  反向代理）吐出一個攔截頁或錯誤頁，同樣是 200，但內容完全不是你的網站。
- 打包/上傳過程如果漏了某個檔案（理論上前面四層驗證會抓到，但如果驗證本身被跳過），
  遠端可能還在用舊檔案，一樣能回 200。

**判準是比對內容，不是看狀態碼。** 最簡單的做法是抓一個「內容應該隨部署變動」的檔案
直接比對，例如部署了新版主題後：

```bash
curl -s https://example.com/wp-content/themes/<主題>/style.css | md5 -q
```

跟本機同一份檔案的 md5 對一下，兩者相同才代表遠端真的是這一版；狀態碼是 200 只是
「有東西回來」的最低門檻，不是「回來的東西是對的」的證明。
