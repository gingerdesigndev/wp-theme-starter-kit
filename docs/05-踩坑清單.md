以下逐條展開成因與處置。

### opcache 餵舊碼

改了 PHP 檔案，重新整理頁面卻看不到變化——不是你改錯地方，是 PHP 的 opcache 還在
餵編譯過的舊版本。開發環境常見（正式站與 Local 都會遇到，一次性驗證用的伺服器如果
沒有持久化 opcache 則不會，但不要假設自己的環境是哪一種，遇到就先重載一次）。

```bash
kill -USR2 "$(pgrep -f 'php-fpm: master' | head -1)"
```

這行對 php-fpm 的 master process 送 `USR2` 訊號，觸發優雅重啟，會清掉 opcache 與
realpath cache。**不重載你會開始修一個不存在的 bug**——反覆檢查程式碼、懷疑自己
邏輯寫錯，實際上程式碼從一開始就是對的，只是伺服器沒在跑它。

### headless 截圖騙人

用 headless Chrome（或任何無頭瀏覽器）截圖判斷版面，看到 header 憑空消失、
版面跑掉——**不代表真的壞了**。

成因：滿版元素（`width:100vw` 搭配負 margin 撐出視窗外）在 headless 環境的算繪，
某些設定下會依「視窗高度」而不是「視窗寬度」出錯，把畫面上半部的內容吃掉。
真實瀏覽器對同一份 HTML/CSS 完全正常渲染。

**鐵律：版面問題自己開真實瀏覽器視窗看，不要只信 headless 截圖下結論。**
`curl` 抓 HTML 比對結構（有沒有那個 DOM 節點）是可靠的輔助，但視覺判斷一律用真實
瀏覽器。

### headless 量不了窄視窗

用 headless Chrome 的 `--window-size=375,...` 想模擬手機版寬度截圖，拍出來的圖確實
標示 375 寬，但**畫面內容其實是用比 375 更寬的視窗排版後再裁切成 375 的**——結果是
右側被硬生生切掉，看起來像嚴重爆版，但那是假象。

原因是部分 headless Chrome 版本對 `--window-size` 有隱性下限（實測會被夾在 500px
附近），小於下限的設定不會真的生效，只是輸出圖片的尺寸被裁切成你要的數字。

**正確做法**：要精準模擬窄視窗（尤其 320～375px 這種手機寬度），改用 CDP 的
`Emulation.setDeviceMetricsOverride`，直接告訴瀏覽器「你現在的視窗就是這個寬度」，
而不是拍完整寬度的圖再裁切。

**驗證方法本身要先驗證**：暫時在頁面兩側各放一條 `position:fixed` 的窄色條，
拍出來的圖色條應該貼齊畫面邊緣；如果色條位置不對，代表你量到的不是真正的窄視窗版面。

### fail2ban

短時間內 SSH 連線失敗次數過多，會被主機的防護機制（fail2ban 或類似機制）暫時封鎖。

**症狀特徵**：`nc -z` 測 TCP port 是通的，但 SSH 一開始交換版本字串就被重置
（`kex_exchange_identification: Connection reset by peer`）——連線根本沒有進到
認證階段，所以跟金鑰對不對、帳號密碼全都無關。

**最容易踩的坑**：以為「等一下再試」是安全的處置。實際上**每一次失敗的連線嘗試，
本身就會把封鎖的倒數重新計算**。所以「等 15 分鐘 → 重試 → 又失敗 → 再等 15 分鐘」
是一個永遠出不去的迴圈——每次重試都在延長封鎖，不是在等它自然解除。

**正確解法**：到主機面板把 SSH 服務**停止、再啟動**。重啟服務（尤其容器化的主機）
通常會清掉封鎖狀態，這比等待可靠得多。完整的判定流程（怎麼分辨是 fail2ban、金鑰
問題、還是服務沒開）見 `docs/04-部署SOP.md` 第四節。

**衍生規則**：想預覽某個操作會動到遠端哪些檔案，用工具內建的 `--dry-run` 之類的
機制在同一次連線裡看完，**不要另外再開一條 SSH 去手動查**——每多開一條連線都會
再消耗一次失敗配額，累積起來就是被封鎖的那一根稻草。

### 頁面快取外掛

安裝了頁面快取外掛（WP Rocket、LiteSpeed Cache、W3 Total Cache 這類）的正式站，
把整頁 HTML 存成靜態檔直接餵給訪客，**改動 theme 檔案不會自動觸發清除快取**——
多數快取外掛只認「內容被更新」（文章、頁面被重新儲存），不認「主題檔案被換掉」。

**驗證陷阱**：帶 query string 的 `curl`（例如加 `?v=時間戳`）能繞過快取拿到即時版本，
會讓你誤以為「部署驗證通過」，但那只證明程式碼本身是對的，**不代表訪客實際看到的
是新版**。訪客請求的是裸網址，裸網址走的是快取。

**鐵律：驗證一定用裸網址**，不要加任何 query string。

快取外掛的清除粒度通常是**逐頁的**：改一個影響全站版型的東西（header、footer、
選單）之後，重新儲存單一頁面往往只清那一頁，其他已經被快取住的頁面仍然是舊版。
**改動若影響全站版型，要逐頁抽驗**，只驗首頁就宣告成功會漏掉內頁還沒更新這件事。

有些快取外掛的行為不對稱：**可能不快取 404 頁面，卻正常快取一般頁面**——如果你拿
一個 404 頁測「有沒有快取問題」，得到「立刻是新版」的結果，不代表其他一般頁面也是
新版，這兩種頁面的快取行為可能完全不同，不能用其中一種的結果去推論另一種。

**「Chrome 對、Safari 錯」十之八九也是它**：頁面快取只餵**未登入**的訪客，
登入者繞過快取直接跑 PHP。所以「管理者在 A 瀏覽器看是新的、訪客／私密視窗在
B 瀏覽器看是舊的」幾乎都是快取造成的假象，不是瀏覽器相容問題——先查快取，
再想相容性。實測部署 PHP 修正後使用者回報「還是一樣」，多繞一圈才發現快取檔
的生成時間早於部署時間。三個實用細節：

- **快取檔自己會告訴你它多舊**：WP Rocket 的快取 HTML 結尾有
  `<!-- ... cached@<epoch> -->` 註解，跟部署時間一比就知道要不要清；
  檔案在 `wp-content/cache/wp-rocket/<網域>/<路徑>/`，逐頁一個目錄，
  **可以只刪出問題那頁的目錄**，不用清全站（清全站的代價見下面
  「清快取之前先確認它需不需要清」）。
- **部署 PHP 之後，受影響頁面的快取一定要跟著處理**——靜態 css/js 有
  filemtime 版本號不受快取影響，但頁面 HTML 是 PHP 輸出的快照，PHP 改了
  快照不會自己更新。
- **草稿頁匿名看得到內容＝它其實不是草稿**。草稿匿名應該 404；私密視窗
  居然渲染出頁面，代表它已被發佈（然後被快取）。這同時是「頁面狀態跟交接
  紀錄不符」的訊號，要回頭更新交接。

### 快取外掛的 Lazy Rendering 會讓 Safari 整塊消失

**症狀**：手機 Safari 捲到頁面最底看不到 footer（或某個大區塊），Chrome 完全
正常；而且**只有某些頁**有這問題。

**成因**：WP Rocket 3.17+ 的「Automatic Lazy Rendering」會挑畫面外的大元素標上
`data-wpr-lazyrender` 屬性，配一條 `[data-wpr-lazyrender]{content-visibility:auto}`
讓瀏覽器延後渲染。Chromium 對 `content-visibility` 的觸發做得好；**Safari/WebKit
有 bug，被標的元素可能捲到了也不渲染**，維持 0 高度——看起來就是那塊「不存在」。
哪些元素被標是逐頁決定的，所以症狀只出現在特定頁面。

**診斷**：①用手機 UA `curl` 該頁，grep `data-wpr-lazyrender` 看哪些元素被標；
②headless 量測「載入後」與「捲動後」的元素高度——被害元素會從 0 長成實際高度、
文件總高度在捲動中變化（正常頁面兩個時點應該一致）。

**處置**：在**佈景**加一條更高權重的排除規則
（`footer[data-wpr-lazyrender]{content-visibility:visible}`，掛全站 inline style），
不要去改外掛的排除清單——外掛設定存在資料庫、不在版控裡，搬站或重灌就遺失，
而且沒人知道當初為什麼要排除。修完記得清該頁快取，排除規則才會進到快取 HTML。

### zh_TW 的自動摘要是「55 個字元」，結尾還帶著實體原文

**症狀一**：文章卡片的摘要怎麼樣都填不滿設計稿的行數，在版型端把截斷字數放寬
也沒用。**成因**：`wp_trim_words()` 的計數方式跟著語系走，zh_TW 翻譯檔指定
「按字元計」——自動摘要在 **WordPress 源頭**就被截成 55 個字元，版型拿到的
字串本來就只有這麼長，下游怎麼放寬都是空的。**處置**：掛 `excerpt_length`
濾鏡拉高字數，且用 `add_filter` / `remove_filter` 把自己的迴圈包起來，
不要污染全站；視覺上的截斷交給 CSS `line-clamp`（會自動補 …），PHP 端只留
一個防超長的安全上限。後台有手動填摘要的文章不受 `excerpt_length` 影響。

**症狀二**：摘要結尾出現「[&he...」這種假亂碼。**成因**：`get_the_excerpt()`
回傳的字串結尾帶著 WP 預設的「 `[&hellip;]`」——是 HTML 實體**原文**，
正常輸出時瀏覽器會把它顯示成 […]；但版型用 `esc_html()` 輸出，實體被跳脫成
純文字原樣印出，再被字數截斷切一半就成了亂碼。**處置**：`esc_html()` 之前先
`html_entity_decode()` 解實體、用正規把結尾的 `[…]` 拿掉，字數才算得準、
結尾才乾淨。

### 換了同名圖檔，前台「看起來沒變」

替換一張同名圖檔（URL 完全沒變）之後前台看起來還是舊圖，先分兩層判定，
不要直接重跑部署：

1. **伺服器端**：`curl -sI` 比檔案 bytes（或抓下來比 md5）——跟新檔一致，
   就是已經換好了，部署沒有失敗。
2. **使用者端**：URL 沒變的圖片會被**瀏覽器自己的圖片快取**餵舊版——這跟
   頁面快取外掛無關，是瀏覽器端的行為。請對方硬重新整理（Cmd+Shift+R）即可。

3. **對方硬重載了還是舊圖** → 這一層是 2026-08-31 補上的：實測請使用者
   Cmd+Shift+R 之後**仍然是舊圖**，伺服器端 md5 卻早就對得上。成因是
   `<img>` 的 URL 沒有版本號——CSS／JS 的排入都帶 `filemtime`，改了就重抓；
   圖片沒有，而且換圖時檔名通常不變，瀏覽器就直接用硬碟裡的、連問都不問。
   沒有 `Cache-Control` 時瀏覽器還會用啟發式快取（依 `Last-Modified` 推算），
   舊檔越久越「新鮮」。

**根治**：版型檔的圖片一律走一支帶版本號的函式，不要自己接
`get_stylesheet_directory_uri()`：

```php
function st_img( $file ) {
	$relative = '/assets/images/' . ltrim( $file, '/' );
	$url      = get_stylesheet_directory_uri() . $relative;
	$absolute = get_stylesheet_directory() . $relative;

	// 檔案不存在就原樣回傳，行為跟沒有這支函式時一樣，不會因此爆掉
	if ( ! file_exists( $absolute ) ) {
		return $url;
	}

	return add_query_arg( 'v', filemtime( $absolute ), $url );
}
```

CSS 裡的 `background-image` 拿不到 `filemtime`，改用手動版本號
（`url("../images/hero.jpg?v=20260831")`），換圖時一起更新。

最容易犯的錯是把第 2 層誤判成「部署失敗」，回頭重跑部署、開始懷疑腳本——
伺服器端 bytes 對得上，部署就已經做完了。但**也不要停在第 2 層**：叫對方
硬重載是治標，第 3 層才是讓這件事不再發生。

### 兩條安靜的 CSS 陷阱（toggle 與 grid）

兩條都是「寫的時候完全合理、壞的時候沒有錯誤訊息」的類型：

- **`[hidden]` 會被元素自己的 `display` 宣告蓋掉。** `hidden` 屬性等同一條
  低優先度的 `display:none`；元素若被 CSS 設了 `display:flex`／`display:grid`，
  toggle `hidden` 屬性完全沒有反應。做 toggle 元件（tab、手風琴、下拉選單）時，
  補一條 `.foo[hidden]{display:none}` 當保險。
- **grid 的跨列 span 會把餘量平分進所跨的每一列**，把相鄰列的間距撐散——
  看起來像間距寫錯了，其實是 span 元素比內容高出來的餘量被 grid 分配掉了。
  在 `grid-template-rows` 末尾補一個 `1fr` 軌道，讓餘量被它吸收。

### 輪播與收縮版面的七條陷阱

同一頁五個輪播的實案裡歸納的，多條踩過不只一次。共同點：都是「寫的時候
完全合理、壞的時候沒有錯誤訊息」的類型。

1. **`grid-auto-columns` 不要用 `minmax(0, X)`。** 下限 0 會讓 grid 為了把
   所有項目塞進可視範圍而一路壓縮（實測 370px 被壓成 177px，輪播完全失去
   意義）。用 `min(370px, 78%)` 給一個不可壓縮的寬度。
2. **flex item 預設不能縮到內容寬度以下**，要三條一起才縮得動又不變形：
   `min-width: 0`（解開最小寬度限制）＋ `max-width: 100%`（配合上一條才
   縮得動）＋ `object-fit: contain`（高度固定時只縮寬度會壓扁）。
3. **一個元素不要同時當分隔線和內文。** 兩者寬度不同時會互相牽制（實測：
   分隔線 68.5%、內文 91.7%，合成一個元素後內文被壓成 68.5% 寬、設計稿的
   兩行被擠成四行）。分隔線改用 `::before` 獨立畫。
4. **輪播軌道的 `max-width` 用 `calc()` 從內距推，不要填估計值。** 軌道自己的
   padding 也算在 `scrollWidth` 裡，要一起加回去；差 2〜8px 就會讓「剛好排滿」
   被判成「捲得動」，前台憑空多一顆按了只捲幾 px 的箭頭。另外
   `scroll-snap-align: start` 預設對齊**內距框**，會讓 `scrollLeft` 停在
   padding-left 而不是 0（看起來沒對齊）——加 `scroll-padding-inline`
   對齊內容框。
5. **RWD 輪播以「完整顯示幾欄」當旋鈕**，不要固定欄寬讓軌道自己算——那樣
   中間尺寸一定會切出半欄。每個斷點先決定要完整顯示幾欄，`max-width` 與
   欄寬都從那個數字推：欄寬取 `min(設計稿欄寬, 平分寬)`。
6. **半張卡就是破版，斷點用逐 1px 掃出來、不要用算式估。** 第 5 條說「以完整
   顯示幾欄當旋鈕」，這條是它的操作方法與一個實測踩到的反例。
   **怎麼找斷點**：用 Playwright 從最窄掃到最寬，每 1px 讀一次「有幾張卡的
   右緣還在軌道內」，變化的那一格就是斷點。實測某輪播是 `813px 起兩張、
   1228px 起三張`——這種數字用 `clamp()` 的內距與間距回推很容易差幾 px，
   而差幾 px 就是「切出半張」跟「剛好排滿」的差別。
   **⚠️ 放不下 N 張時退到 N-1 張填滿，不要退成一張滿版。** 實測把
   768～812px 做成「一張滿版」，卡片被撐成 714px 的巨無霸，使用者一眼就看出
   不對。當時的想法是「延續手機的做法」，但手機的容器寬只有 3xx，768 的容器
   有 714——**同一條規則換一個容器寬度，結果可以差很多**。退到兩張是 349px，
   比設計稿的 370 略窄，那才是對的方向。
   **驗收**：改完掃一次全範圍（例如 360～1500px 每 1px），確認**每一個**輪播
   在**每一個**寬度都沒有露出半張，再說做完了。

7. **自動流動的輪播（marquee）不要加 `scroll-snap`**，會跟自動推進打架、
   變成一頓一頓的。自動流動用 rAF 推 `scrollLeft` 而不是 CSS transform
   （容器維持 `overflow-x: auto`，手機仍可自己滑）；內容複製一份做無限循環
   （複製品標 `aria-hidden`）；hover／focus／按住時暫停；捲出畫面或切分頁時
   停掉 rAF；尊重 `prefers-reduced-motion`。

### 選單存資料庫，footer 跟著主題部署

站上「看起來都是導覽」的東西，存放位置其實分兩種，部署行為完全不同：

- **後台選單**（外觀 → 選單）存在**資料庫**——不進 git、不隨主題部署，
  每個環境各自維護，改它要進後台（或走 REST），改完通常還要清快取。
- **footer / header 裡硬編在模板檔的連結**，隨主題檔案部署——`deploy.sh`
  跑完就是新的。

這個分野本身就是診斷線索：部署主題後「footer 的連結更新了、導覽列還是舊的」
**不是部署失敗**——footer 跟著檔案走所以變了，導覽列存在 DB、而且各頁快取住的
HTML 裡還是舊的 `href`。處置是改資料庫裡的選單＋清快取，不是回頭懷疑部署。

連帶一條：**選單項目的 db_id 在本機與正式站幾乎必然錯位**（兩邊各自建資料列、
各排各的編號，可能整組平移幾號）。照本機的 db_id 上正式站改選單，會改到
**別的項目**。驗收也有陷阱——用「某連結有沒有出現在 nav」驗收，對「改錯項目」
完全不敏感：改錯項目一樣會讓那個連結出現、一樣「通過」。正確驗法是按項目
**標題**對照：確認那個 db_id 的 title 是預期的項目、**且** url 也是對的，
兩者同時成立才算過。

### 瀏覽數統計外掛被整頁快取架空

多數瀏覽數外掛靠 PHP 在頁面渲染時累加計數——而被整頁快取住的請求**根本不執行
PHP**，於是瀏覽數長期嚴重低估、熱門排序幾乎不動，而且沒有任何錯誤訊息。
裝了整頁快取外掛的站（多數正式站都有）要用瀏覽數外掛，**計數模式必須改成
JS／AJAX 類**（外掛通常有 `js`、`rest_api`、`fast_ajax` 這類選項），讓計數請求
繞過頁面快取，否則等於白裝。

兩個相關細節：這類外掛的「熱門文章」查詢常靠 filter 掛排序，用 `get_posts()`
查要帶 `'suppress_filters' => false`（它預設會關掉 filter，排序條件悄悄失效）；
還沒有任何瀏覽紀錄時，熱門查詢回空集合是預期行為（多半是 INNER JOIN），
「熱門區塊沒東西」在累積出資料前不是壞掉。

### macOS AppleDouble

macOS 的 BSD `tar` 打包時，會把檔案的延伸屬性（extended attributes，例如 Finder
的標籤、來源資訊）額外包成一份隱藏的「影子檔案」，檔名是原檔名加上 `._` 前綴。
在 Linux 主機上解壓，這些影子檔案會變成一堆看起來莫名其妙的 `._*` 垃圾檔，混進部署
目錄裡。

**根治方法**：打包時加上環境變數 `COPYFILE_DISABLE=1`：

```bash
COPYFILE_DISABLE=1 tar czf archive.tgz -C <目錄> .
```

實測比對：不加這個變數，一次打包會夾帶近 20 個垃圾檔；加了之後是 0 個。這是
macOS 專屬的問題，在 Linux 上開發不會遇到，但只要你的開發機是 Mac，這一步就不能省。

### symlink 斷鏈

早期常見的本機開發做法是：把主題 repo 放在別的地方，再用 symlink 連到 WordPress
站台的 `wp-content/themes/` 底下。這個做法有兩個實測會炸的問題：

1. symlink 斷鏈（目標路徑改變、專案搬家）會讓 WordPress 找不到主題檔案，站台直接
   500 或路徑判斷全部錯亂。
2. 部分伺服器環境的 `realpath` 快取對 symlink 的行為不穩定，會讓「症狀時有時無」，
   排查起來比直接壞掉更難定位。

**正確做法：官方就地開發（in-place development）**——把 repo 本身直接設定成
WordPress 站台的主題資料夾，不透過 symlink 中介。這是 WordPress 官方建議的開發
方式，也是本起案包預設假設的環境結構。

### HTTP 200 不等於成功

`curl` 拿到 200 只代表「伺服器有回應內容」，不代表「回應的內容是你要的那個版本」。
快取住的舊版頁面、中繼架構的暫態攔截頁、還沒更新完成的部署，都可能回 200。

**判準是比對內容，不是看狀態碼。** 至少要抓一個「內容應該隨改動而變」的東西直接比對
（例如主題的 `style.css` 內容 md5、或頁面裡某段應該已經更新的文字），確認兩邊真的
一致。完整討論見 `docs/04-部署SOP.md` 最後一節。

### 顯示判斷分散兩處

「要不要顯示某個區塊 / 某段文字」這種條件判斷，如果在程式碼裡出現兩份各自獨立的
邏輯（例如桌機版一份、手機版另一份；或是模板檔一份、共用函式又一份），會製造出一個
很難查的坑：**本機因為有測試資料，兩份判斷剛好給出一致的結果，看起來完全正常；
正式站因為某個欄位還沒填值，兩份判斷的結果分歧，其中一份顯示、另一份不顯示**，
於是版面在正式站出現本機重現不出來的異常。

**規則：同一件事的「要不要顯示」判斷，全站只能有一份實作**，其他地方呼叫同一份，
不要各自重寫一次相近但不完全一樣的條件式。

### 回退值＝真實值

自訂欄位（ACF 或類似機制）常見的防呆設計是：欄位沒填值時，回退到一個看起來合理的
預設值，避免整個區塊開天窗。這個設計有一個隱藏的驗證盲點——**如果那個預設值剛好
跟「欄位確實接通並填了正確的值」長得一模一樣，你在前台看到正確的畫面，完全無法
分辨欄位系統到底有沒有真的接上**。

實測踩過兩次：一次在本機、一次在正式站，都是接欄位接完看前台顯示正常，事後才發現
其實整條路徑一路走的都是回退值，欄位系統從沒被真正呼叫過。

**判別方法**：
1. **清空欄位值再看一次**——如果清空後畫面完全沒變，代表你看到的原本就是回退值，
   不是欄位值。
2. **查資料庫**：確認欄位對應的值真的被存進去了，不是靠猜。
3. **臨時土法**：後台值後面手動加一個明顯的標記字串，前台如果出現那個標記，
   才確定讀到的是資料庫的值而不是回退值。這個方法快，但會短暫改到看得到的內容，
   測完記得改回來。

**正式站如果同時有頁面快取**，還會疊加一層假象：快取住的舊頁面也會讓你以為看到的
是最新狀態。分辨方法是比對快取檔案的產生時間跟你部署/填值的時間，快取時間早於
你的改動，代表你看到的就是舊快取，跟欄位系統有沒有接通無關。

### 硬編設計稿的分類清單

設計稿上常常會畫出一份分類清單（衛教文章分類、商品分類、標籤列表這類），乍看只是
排版用的靜態清單，直接把清單文字寫死進模板很省事——**但設計稿列的清單跟站上資料庫
裡真實存在的分類，經常對不上**。實測案例：設計稿列 12 個分類，站上實際有 18 個
子分類，其中只有 4 個名稱完全一致。

硬編清單造成的問題不是「看起來不對」而是**產生死連結**——清單裡有的分類，網站上
根本沒有對應的內容或連結目標，點下去是空頁或錯誤頁。

**規則：凡是設計稿畫出「一份清單」（分類、標籤、選單、地區、任何來自後台可管理資料
的列表），一律讀 WordPress 資料庫的真實資料生成，不要照畫面文字硬編。** 兩者對不上
時，把差異當成「內容管理該調整的事」回報給客戶或內容負責人，不要用硬編掩蓋過去。
讀真實資料的清單，未來後台調整分類時網站自動跟著對，不需要再改一次程式碼。

同一個道理也適用於「欄數固定寫死」——例如分類 tab 按鈕的欄數，設計稿畫的是固定
6 欄，但真實分類數量是由後台決定的變數，用能自動撐開/縮小欄數的排版方式（例如
CSS Grid 的 `auto-fit`）取代寫死的固定欄數，才不會在分類數量改變時版面跟著壞掉。

### 頁面建構器吞掉 header/footer

從舊的頁面建構器（Elementor、Divi 這類，常搭配它們自己的 Theme Builder 功能）遷移
到自刻主題時，最容易踩、代價也最高的一個坑：**只要頁面建構器的 Theme Builder 功能
還在啟用，即使你已經把某個頁面的內容換成自刻主題的版面，這個頁面的 header 與 footer
仍然可能被頁面建構器接管、蓋掉主題自己的版本**。

**機制**：頁面建構器的 Theme Builder 用 output buffering 攔截 WordPress 的
`get_header()` / `get_footer()` action，改印它自己指定的範本；如果沒有對應範本，
就什麼都不印——這解釋了為什麼 header 會「憑空消失」而不是「顯示成別的樣子」。
症狀特徵：`wp_body_open()` 這類鉤點有正常執行（追蹤碼出得來），但主題自己的
`<header>` 標籤完全不出現在渲染結果裡。

**正確順序（硬依賴，不能顛倒）**：

```
其餘頁面遷移完 → 才能停用頁面建構器 → header/footer 才會是自刻主題的
```

只要還有頁面依賴頁面建構器渲染內容，現在停用它會讓那些頁面全部塌掉。**先把其餘
頁面遷移完，最後才處理頭尾**，這條踩過一次代價很高（一次遷移的頁面數以個位數計，
一次性停用會讓所有頁面同時故障），不要為了「先把頭尾修好看」而提前停用。

**進階繞法**：如果暫時不想／不能停用頁面建構器，但想讓某個特定頁面（例如已經
遷移完成的首頁）先套用自刻主題的頭尾，可以繞過頁面建構器攔截的那兩個 action——
新增一個範本檔案，直接用 PHP 的 `require` 載入 `header.php` / `footer.php` 的內容，
**不呼叫** `get_header()` / `get_footer()`，那兩個 action 就不會被觸發，頁面建構器
自然不會介入。這個做法讓單一頁面提前繞過劫持，不必等到整站遷移完、也不影響其他
還在依賴頁面建構器的頁面。全站遷移完、正式停用頁面建構器之後，這個繞道範本可以刪除，
改回一般的 `get_header()` / `get_footer()` 呼叫。

### Figma 設計稿與素材的四個坑

2026-08-31 做一組側邊懸浮按鈕與一個工具頁時，四個都踩到。共同點：**你以為在讀
設計稿，其實只讀到它的一部分**。

1. **效果常常掛在父群組，不在你選到的那一層。** 使用者回報「icon 有陰影」，
   但他在 icon 圖層的 Effects 面板找不到任何東西，我也在該節點的 API 回應裡
   看到 `effects: []`。實際上陰影掛在包住三顆按鈕的**群組**上。
   **處置**：找不到就往上層找，或直接抓整份檔案掃一遍所有帶 `effects` 的節點：
   `GET /v1/files/{key}` 之後遞迴找 `effects[].type` 結尾是 `SHADOW` 的節點。
   群組陰影吃的是群組的合成 alpha——子元素彼此不重疊時，逐個套用的結果等同
   群組套用，可以安心拆成單一元素的 CSS。

2. **CSS `drop-shadow()` 的 blur 跟 Figma 的 Blur 不是 1:1。** 設計稿是
   `x .58 / y .58 / blur 2.3 / #000 61%`，照抄進 CSS 之後又淡又散——實測擴散到
   6px 才收，設計稿只有 2px。
   **處置**：用 Figma 的 image API 把該節點算繪成 3 倍 PNG
   （`GET /v1/images/{key}?ids=...&scale=3`），跟自己的算繪結果**逐像素比對
   邊緣的明度曲線**，掃 blur × 不透明度找最小誤差。該案最後是
   `1.2px / 100%`（誤差 4.1，次佳 7.2），也就是「縮緊模糊、加深顏色」去補償。
   憑感覺調不會收斂，而且下一個人會再調一次。

3. **Figma 的原始上傳圖是 RGBA，邊緣可能有 1px 全透明。** 攤平成 JPEG／WebP
   時，全透明像素存的 RGB 是 `(0,0,0)`——透明度被丟掉、黑色被留下，就變成
   畫面上那條黑線。實測 `dean-photo` 的最下一列與最右一行 alpha=0，裁掉外圈
   1px 之後 alpha 範圍就是 `(255,255)`。
   **不是設計師畫了黑線**，是轉檔沒處理透明通道。攤平前一律先用白底
   （或該區塊實際底色）合成，不要直接 `convert('RGB')`。

4. **修圖的優先順序，不要跳級。**
   1. **回頭拿原始素材**——`GET /v1/files/{key}/images` 會回傳所有 `imageRef`
      對應的原始上傳檔網址，那是設計師丟進 Figma 的原檔，比任何算繪或截圖都好
   2. **誠實裁掉**沒有資料的部分，並**同步改版型檔寫死的 `width`／`height`**
   3. **不要用相鄰像素去補。** 那等於憑空生成原本不存在的畫素，而且是在已經
      有損壓縮的檔案上再壓一代

   實測踩過：第一次修 `dean-photo` 用「複製相鄰像素蓋掉黑邊」，被使用者當場
   否決——「圖片應該是怎樣就是怎樣」。當時的藉口是「版型檔寫死了尺寸，改尺寸
   要動版型」，但**那正是應該去改版型檔的訊號**，不是繞過它的理由。

**前提**：以上都需要讀得到設計稿。Figma 的 MCP 連接器若是走 claude.ai 的
互動式授權，**換一個 session 就不在了**（交接文件寫「已連上」不代表現在連得上），
而 WebFetch 打設計稿網址一律 403。確認工具清單裡沒有 Figma 工具時，除了
`AGENTS.md` 寫的兩條路線，還有第三條：請使用者產一個**唯讀**的 Personal Access
Token（Settings → Security → Personal access tokens，scope 只開 File content
read-only），存進 repo 外的檔案，之後用 REST API 讀。這條不需要桌面版、
不需要付費席次。

### 照設計稿逐圖層抄字距行高，驗收時會被整批退

**症狀**：切版時忠實照設計稿逐圖層的數值做——某段文字圖層 letter-spacing 是 0
就寫 `letter-spacing: normal` 蓋掉全站值、行高標 1.2 就寫 1.2、設計稿在哪裡換行
就放 `<br>`。驗收時被使用者一條一條退：「這段字距怎麼特別窄」「這行擠在一起」
「手機上多了孤字行」，最後整批改回全站值。

**成因**：設計稿逐圖層的排版數值有很多是**設計工具的預設殘留**，不是設計決策；
而使用者驗收時看的是「整頁一致不一致」，不是「跟稿差幾 px」。實測一次驗收清掉
五處字距歸零、一處 1.2 行高、兩處指定 `<br>`——全部是先照稿做、再被退回來的。

**處置**：
- **基礎排版（字距、行高）用全站值起手**；設計稿圖層標了不一樣的值，先當可疑，
  真的要偏離全站值時在 CSS 註解寫明理由。
- **設計稿指定的換行位置（`<br>`）只在對應的版面寬度下成立**。手機斷點把 `<br>`
  關掉（`br { display: none }`）讓文字自然流動，配 `text-wrap: balance` 配平
  行長，就不會掉出「會。」這種單字行——這招對「使用者字級調大」也免疫。
- **手機版不要自作主張拿掉設計稿的視覺處理**。實例：照片上的白色刷淡漸層，
  切版時判斷「手機改上下排、文字不壓在照片上，漸層沒意義」就關掉——被退。
  漸層是照片視覺的一部分，不是只為文字墊底的功能件。拿不準就保留。

### zsh 不是 bash

macOS 的預設殼是 **zsh**。同一段指令在 bash 正常、在 zsh 會安靜地做別的事或直接
報錯，而且錯誤訊息完全看不出是殼的問題：

- **不做單字分割。** `FILES="a b c"; for f in $FILES` 在 bash 會跑三次，在 zsh
  `$f` 是整串 `"a b c"`、只跑一次。實測拿來逐檔比對 md5，結果是「13 個檔案只驗了
  1 個」還顯示成功。**處置**：清單寫進檔案，用 `while IFS= read -r f; do ... done < 清單`。
- **`read -p` 不是「顯示提示字」而是「從 coprocess 讀取」**，會回
  `read: -p: no coprocess`。zsh 的寫法是 `read -rs "t?提示字: "`。
- **未加引號的 `--include=*.php` 會被當成 glob**，沒有符合的檔案就整條指令中止
  （`no matches found`）。**處置**：這類含 `*` 的參數一律加引號。

**教使用者在他自己的終端機執行指令時，這件事會放大成信任問題**——他照貼三次
都失敗，會覺得是自己弄錯。給指令前先想清楚他的殼是哪一種；不確定就外面包一層
`bash -c '...'`，或改用最不容易貼壞的方式（例如叫他用編輯器開檔案手動填）。
包 `bash -c` 時注意**開頭的 `bash -c ` 很容易在複製時掉字**，實測發生過。

### 應用程式密碼只認 REST

想用 `curl --netrc-file` 帶著應用程式密碼去抓一個**草稿頁面的預覽**來驗證版面，
會拿到 **404**。WordPress 的應用程式密碼認證只作用在 REST API（與 XML-RPC），
一般的頁面請求不吃這組憑證。

**處置**：草稿頁面的視覺驗證只能請使用者登入後台預覽。你能自己驗的是：
REST 回應裡的 `template` 有沒有套對、ACF 欄位值有沒有寫進去、以及**在本機**
把同一支範本渲染出來看。交付時要**明講哪一項你沒能自己驗證**，不要用
「已完成」帶過。

### 清快取之前先確認它需不需要清

部署後準備清頁面快取，發現快取目錄有 56MB（WP Rocket 2.6M ＋ FlyingPress 56M
＋ used-css 21M），正要動手刪——**先停下來驗證**。

實測：透過 REST 更新內容區塊之後，快取外掛**已經自動 purge 過了**。用一般訪客的
UA 抓四個頁面，拿到的全是新內容。手動刪那 56MB 只會讓網站接下來一段時間變慢，
什麼問題都沒解決。

**處置**：先用真實訪客的 UA `curl` 幾個代表性頁面，grep 新內容的特徵字串。
拿得到就什麼都不用做。真的要清時，優先找外掛自己的清除入口，而不是直接刪檔案；
特別注意 **`used-css`／`critical-css` 這類「移除未使用 CSS」的產物**——DOM 改過
之後這種快取是真的會出錯的一類（它可能把你新加的 class 當成沒用到而刪掉）。

### 母主題的透明頁首會疊在你的版頭上

做一個「全寬版頭圖」的新範本，上線後版頭頂端被導覽列吃掉一截。成因是母主題的
透明頁首**不是背景透明而已，是整列絕對定位疊在內容上**——Blocksy 的 static CSS
就寫著 `[data-transparent]{position:absolute;top:0;left:0;right:0}`。客戶如果把
選單背景改成不透明，這個設計就只剩遮擋效果。

**處置**：在該範本自己的 CSS 裡把它推回文流（用比母主題高一級的選擇器）：

```css
.ct-header [data-transparent] { position: static; }
```

**這條會重複踩**：它是「每個新的全寬版頭範本都要各自處理一次」的類型——樣式檔
按範本載入，A 範本修好不會惠及 B 範本。做新的全寬版頭時主動檢查，不要等回報。
本案就是首頁範本早就修好、三週後做工具頁時又踩一次。

### 重新編碼有損圖：品質參數用掃描的，不要憑感覺

要修一張已經是 WebP／JPEG 的圖（裁切、去邊、換尺寸）就必須重新編碼。憑感覺選
`quality=92` 的結果是**檔案漲了 25%～52%**，對載入速度是實質損失。

**處置**：寫個小迴圈掃品質參數，同時輸出「檔案大小」與「相對於原圖的 PSNR」，
選**PSNR 到頂之後最小的那一個**。原檔本身已是有損壓縮，PSNR 會有天花板
（實測某 WebP 卡在 30.2 dB，`q=85` 和 `q=90` 同樣是 30.2，但檔案差 34%）——
超過天花板再往上加只是把檔案變大，畫質一點都沒有變好。

更好的做法是**回頭從原始 PNG 產出**，只壓一代；在已經壓過的檔案上再壓一次，
不管參數多高都回不去。

### 改分類 slug 後新網址 404：rewrite flush 只在後台情境跑

**症狀**：用 REST（或 wp-cli）改了分類的 slug，新網址 `/category/<新 slug>/` 回 404，
或者更陰——被 WP 的 `redirect_guess_404_permalink()` **猜成一篇名字相近的文章**
而 301 過去，看起來「有東西」，其實頁面根本沒建出來。沒改名的分類一切正常。

**成因**：Rank Math 這類 SEO 外掛的「移除分類 base」是 per-category 的 rewrite rules。
改 slug 時外掛只會**排程** flush（寫一個 option 旗標），而 flush 本體掛在
**admin 情境的 `init`**——前台流量永遠不會跑到它，所以不登入後台一次，規則永遠不更新。
`redirect_guess_404_permalink` 又把 404 掩蓋掉，讓你以為是別的問題。

**處置**：打一發 `POST /wp-admin/admin-ajax.php`（body 隨便，例如 `action=heartbeat`）
就進了 admin 情境、跑過 `init`，flush 立即生效，不用登入也不用進後台。
日後任何「建／刪／改分類之後彙整頁 404」先想到這條。
驗收時看「是否 200 **且落在正確頁**」——301 也要追它轉去哪，別把猜測轉址當成功。

### 外來參數撞 WP 查詢變數：`?m=1` 讓整頁變 404

**症狀**：從外部系統（Blogger 對手機訪客會先加 `?m=1` 再套轉址）帶進來的網址，
路徑完全正確，卻整頁 404；桌機（沒有那個參數）正常。

**成因**：`m` 是 WordPress 的**公開查詢變數**（年月彙整），`m=1` 被解讀成「西元 1 年」，
與網址條件 AND 起來查無文章。任何外部系統帶進來、剛好與 WP 公開查詢變數同名的參數
（`m`、`p`、`s`、`cat`、`page`、`tag`…）都有同類問題。

**處置**：`functions.php` 掛 `request` filter，在前台把值恰為 `'0'`／`'1'` 的 `m` 拿掉；
`is_admin()` 要放行——後台文章列表的月份篩選用的是同一個變數。
驗證可以拿「尚未部署的正式站」當改前對照組：同一批網址正式站 404、本機 200，
就證明是這支 filter 的效果。而且**帶查詢字串的請求不進頁面快取**，部署後立刻能驗。

### 清快取的 REST 重存法分三種，不要照抄 pages 的做法

用「REST 重存、觸發 `save_post`、讓快取外掛清該頁」是可用的手法（見
`docs/04-部署SOP.md` 第六節），但三種內容的做法不一樣：

| 內容類型 | 送什麼 | 為什麼 |
|---|---|---|
| **pages** | `POST /wp/v2/pages/<id>`，body `{"menu_order": <原值>}` | 不影響呈現的欄位 |
| **posts** | `POST /wp/v2/posts/<id>`，body `{"status": "publish"}`（先確認原本就是 publish） | posts 的 REST 回應**根本沒有 `menu_order`**，照抄會 KeyError |
| **分類彙整頁** | `POST /wp/v2/categories/<id>`，body `{"slug": "<原值>"}` | 彙整頁不是 page，重存文章清不到它；原值重存 slug 會觸發 `edited_term`，快取外掛會清該彙整頁 |

三種都是「原值重存、內容零變動」。另外**WP Rocket 沒有 purge 的 REST 路由**
（實查 `/wp-json/` 的 `wp-rocket/v1` 只有 rocketcdn／cpcss／options-export 這幾支），
要清全站只能請使用者進後台按。部署後 `?nc=…` 看到新版、裸網址還是舊版，就是這個狀態，
不是碼沒上去。

### 兩站 ID 必不相同的四種東西：一律先依 slug 查 id

本機與正式站各自建資料列、各排各的編號，**四種 ID 幾乎必然錯位**，而且錯位不報錯——
照本機 ID 去改正式站，會改到別的東西：

1. **attachment ID**（圖片欄位存的值，見 `docs/02-ACF規範.md` 第八節）
2. **page／post ID**（連 ACF 欄位群組的 location 都不要綁它，見 02 第六節）
3. **term_id**（分類、標籤；兩邊可能整組平移幾號）
4. **選單項目的 db_id**（見上方「選單存資料庫」一條）

**紀律**：動之前先 `GET /wp/v2/<type>?per_page=100` 按 slug／title 列出來核對 id，
不沿用本機 ID、也不信舊筆記裡的數字。連帶要知道：**兩站的 term slug 本身也可能不同步**
（一站改過名、另一站沒跟），查 id 之前先確認 slug 對得上，否則查到的是空的。
程式碼裡若要依分類做邏輯，用 slug 查 `get_term_by()`，不要寫死 id。

### 回退值紀律的兩面：同欄位兩處回退值不同；空字串會把缺值變成消失的元素

`docs/02-ACF規範.md` 第三節講的是「回退值＝真實值時驗不出接通」。這條是它的續篇，
實案是**同一個電話欄位、兩支呼叫傳了不同回退值**：頁尾傳寫死的電話號碼、
側邊快速鈕傳 `''` 想「沒填就不顯示那顆」。結果正式站那個欄位從來沒填過，
電話鈕整顆不見、頁尾卻「看起來正常」——同一頁上一邊有、一邊沒有，而且本機
（DB 有值）怎麼驗都驗不出，因為兩站的差異在 DB 不在 code。

**判準**：
1. 有寫死回退值可用的欄位（電話、地址這種不會變的），**一律傳同一份回退值**；
   不要為了「沒填就不顯示」傳空字串——那會把資料缺口變成看不見的缺件。
2. 傳空字串只留給「沒有值就真的不該有這個東西」的欄位（例如沒有 LINE 網址時，
   給一顆按不出東西的鈕更糟）。
3. **同一個欄位在不同檔案的回退值要一致**，不一致就會出現「頁尾有、按鈕沒有」。

**驗法（不寫壞 DB）**：wp-cli 暫時把 `options_<欄位名>` 清空 → curl 前台數元素 →
立刻還原（`trap ... EXIT`）。⚠️ 用 `add_filter('acf/load_value/name=xxx')` 模擬空值
**會假報通過**（值已被 ACF 快取住），別用。

### 「查不到就整塊不輸出」的防呆，同時也是錯誤靜默

**症狀**：客戶回報「正式站的某頁少了一組」。curl 實查正式站只渲染兩組、
**沒有任何錯誤訊息**。根因是那一組對應的子分類 slug 兩站不同步，模板用
`get_term_by()` 查不到 → 被該檔刻意設計的「空組不輸出、不留空標題」規則整組略過。

**真正要記的是機制，不是這個 slug**：「查不到就整塊不輸出」是防呆（避免線上留一個
空標題），但它同時也會把「slug 打錯／兩站不同步」這種**設定錯誤**一起吞掉——防呆與
錯誤靜默是同一個機制的兩面。凡是有這種回退的地方（分組清單、相關文章的遞補、
pattern 自帶的查詢），**兩站 term slug 必須列進部署後的逐項抽驗**。

**處置**：驗收要數「該出現幾組／幾張卡」，看 HTTP 200 和沒有 PHP 錯誤是驗不出來的。
過渡期可以給每組一個 `alias` 別名清單（正規 slug 找不到才依序往下試），兩站統一後清空。
**驗別名分支要刻意製造它**：本機本來就有正規 slug，直接 curl 只會走正規那條；
用 wp-cli 暫時把本機 term 的 slug 改成另一站的值 → curl 數組數 → `trap` 還原。

### 依分類改作者／meta 的 hook 要掛 `wp_after_insert_post`，不是 `save_post`

**症狀**：「發文時依分類自動指派作者」在本機全過，上正式站後**新文章第一次存檔不換作者**，
第二次存才對。

**成因**：區塊編輯器走 REST，核心的順序是 `wp_insert_post`（**`save_post` 在這裡觸發，
分類還沒掛上**）→ `handle_terms` 掛分類 → `wp_after_insert_post`。所以 `save_post` 裡
讀 `wp_get_post_categories()` 第一次永遠是空的。

**處置**：依分類動作者／meta 的邏輯一律掛 `wp_after_insert_post`。
**本機要用 `rest_do_request()` 走 REST 路徑測**——`wp_insert_post()` 直接帶 `post_category`
測不出這個時序差，會讓你以為全過。REST 回應的 `author` 是換掉前的值（控制器先取好
`$post` 才呼叫 hook），需要的話用 `rest_prepare_post` 重讀。
連帶：這類「規則表」跟客戶討論時用「誰發文 × 什麼分類 → 結果是誰」的表格講，
不要用「改窄」「強制」這類抽象詞，否則會被理解成相反的意思多繞兩輪。

### 區塊編輯器裡「存檔後顯示一次」的伺服器端旗標會被核心吃掉

**症狀**：想做「存檔時發現違規 → 下次載入編輯頁跳一次警告」，用 post meta 記旗標、
`admin_notices` 或 `enqueue_block_editor_assets` 讀到就顯示並刪掉。部署後使用者**什麼都沒看到**，
PHP 端模擬（REST 存檔＋跑一次 hook）卻全過。

**成因**：區塊編輯器存檔＝`POST /wp/v2/posts/<id>` 之後，核心會另外
`POST post.php?…&meta-box-loader=1` 去存 meta box，`redirect_post()` 轉址到
`post.php?post=<id>&action=edit`，瀏覽器的 fetch 跟著轉址**把整個編輯頁再渲染一次**——
旗標在那次背景載入被讀走刪掉，使用者真的重整時已經沒了。另外區塊編輯器的 CSS
把 `#wpbody-content` 底下傳統 `admin_notices` 全部 `display:none`，所以第一版連顯示的
機會都沒有。

**處置**：要在區塊編輯器提示，只能在 **JS 端存檔當下判斷**：`wp.data.subscribe` 看
`isSavingPost()` 轉 false 後比對 `getCurrentPost()`，再
`wp.data.dispatch('core/notices').createWarningNotice()`；核心自己也是用
`wp_add_inline_script('wp-notices', …)`。任何「看過即刪」的伺服器端旗標都要先問
「存檔後有沒有背景請求也會載入這頁」。**這類 UI 行為一定要有人在瀏覽器實看**；
用瀏覽器開後台時 `read_network_requests` 看得到那趟 meta-box 請求，實看二十分鐘就能定案。

### TinyMCE 設定字串不能含雙引號；給客戶的段落樣式做成 `h4.class`

**症狀**：改了 `tiny_mce_before_init`（或 ACF 的 `acf/fields/wysiwyg/toolbars`）之後，
**某一個後台設定頁的所有編輯器都起不來**，其他頁正常；`php -l` 過、前台量測全過。

**成因**：核心輸出 `tinyMCEPreInit` 時字串值直接 `'"' . $value . '"'` **不跳脫**，
`content_style` 裡一個 `content:"・"` 就讓整段 `<script>` 語法錯誤。只在那個 `?page=`
發作，離線測試完全看不出。**處置**：CSS 的 `content` 用單引號。
驗法：Local 的 php CLI 載 `wp-load.php`＋`wp-admin/includes/admin.php`、
`add_filter('user_can_richedit','__return_true')`（CLI 預設 false，不加 mceInit 是空的）、
`wp_editor()` 後抓 `_WP_Editors::editor_js()` 的輸出，丟 node `new Function('tinymce', src)` 跑一次。

**連帶**：給客戶用的「段落樣式」（小標、警語）做成**標題元素** `h4.class`，不要 `p.class`——
TinyMCE 在帶 class 的 `<p>` 尾端按 Enter 會把整個 p 連 class 複製到新段，客戶打完小標
按 Enter 得到第二個小標會以為壞了；標題元素尾端 Enter 固定給裸 `<p>`。
`style_formats` 用 `attributes:{class:'…'}`（設成這個值、可清掉）不用 `classes`（疊加）。
前台 CSS 要對那個 h4 明寫 `margin:0;font-size:1em;line-height:inherit;letter-spacing:inherit`。
原則一句話：**編輯器寫 class、CSS 只認 class**，不要靠 `:has()` 猜結構。

### 自訂欄位上「快速編輯」：只攔 `_inline_edit` 那次提交

**症狀**：給文章列表的「快速編輯」加了自訂 checkbox，存了之後沒問題；但到編輯頁
用 ACF 勾了同一個欄位再存檔，**值又被改回去**。

**成因**：快速編輯與編輯頁存檔都走 `save_post`。如果 `save_post` 不分辨提交來源，
編輯頁存檔時表單裡沒有那個 checkbox（＝不勾），就把 ACF 剛存的值蓋掉。

**處置**：`save_post` 只處理帶 `_inline_edit` nonce 的那次提交（`check_admin_referer`），
編輯頁的儲存交給 ACF。快速編輯的表單模板全站只輸出一份、不能印單篇的值，
值要從該列的欄位 `data-*` 讀：列表欄輸出 `data-featured="1"`，JS 用
`wp_add_inline_script` 掛 `inline-edit-post`、包 `inlineEditPost.edit` 回填。
寫 meta 比照 ACF 的格式（'1'／'0'，不 `delete_post_meta`），兩邊才互通。

### ACF options 母選單：redirect 型的 slug 會被改寫，子選單順序＝呼叫順序

三條都是「掛得上去但沒人告訴你哪裡不對」的類型：

1. **redirect 型母選單（`acf_add_options_page(['redirect' => true])`）的頂層 slug 會被
   ACF 改寫成第一個子頁的 slug**（連全部子頁的 parent_slug 一起改）。之後想用
   `add_submenu_page('<註冊時的 slug>', …)` 掛捷徑，會掛進一個**沒人渲染的孤兒桶**，
   後台完全不顯示、也沒有錯誤。解法：hook 掛 `admin_menu` priority 100，直接掃
   `global $submenu` 找「裝著已知子頁 slug 的那個桶」當 parent。純 `add_menu_page`
   的母選單不會被動。
2. **子選單順序＝`acf_add_options_page()` 的呼叫順序**（ACF 在 `admin_menu` 99 依
   註冊順序 `add_submenu_page`），不是靠 `menu_order` 參數——要排序就調整呼叫順序。
3. **頂層選單順序看 `position` 數字**，撞號時 WP 用 md5 派小數遞補、順序不可控。
   每個頂層選單給唯一整數。

無頭驗後台選單的做法：Local 的 php CLI、`--context=admin`、`wp_set_current_user(管理員)`
後 `$menu=[];$submenu=[];do_action('admin_menu','')` 再 dump。⚠️ 別 `require
wp-admin/includes/menu.php`（整組 fatal）；首跑可能拿到改動前的舊值，**連跑兩次一致才算數**。

### `big_image_size_threshold` 預設 2560：上傳建議不要寫得比它大

WordPress 上傳超過 2560px 的圖會自動縮成 2560（`big_image_size_threshold`）。
給客戶的「建議上傳尺寸」如果照設計稿輸出寫 2880×1400，客戶上傳後看到變 2560 會以為
上傳失敗。寫 2560 寬的對應尺寸。主題內建、不經媒體庫的回退圖可以維持 2880，
但文件要註明「兩個數字不同是刻意的」。

### 全站 noindex 時 sitemap 404、llms.txt 空、canonical 不輸出，是同一個開關

驗收清單上看起來是三個 bug：`post-sitemap.xml`／`page-sitemap.xml`／
`category-sitemap.xml` 404、`llms.txt` 只剩 Sitemaps 一節、頁面沒有 `<link rel=canonical>`。
查根因只有一個——全站還是 `noindex,nofollow`，SEO 外掛對 noindex 的內容型態全部不輸出。
**開索引前修不掉、開索引後不用修。** 開索引那天要回頭驗這三件，驗收清單記成一條。

### 備份外掛的備份檔在 nginx 主機可公開下載

**症狀**：WPvivid 在主機上產生的備份 zip，用直接網址抓回 200——資料庫備份含後台帳號
email、密碼雜湊、表單送出紀錄（可能有客戶的客戶資料）。

**成因**：外掛靠 `/wp-content/<備份目錄>/.htaccess` 擋，**nginx 不讀 .htaccess**。
檔名的亂碼是依時間產生的，可被猜到。（All-in-One 的 `ai1wm-backups` 有擋、回 403。）

**處置**：每次在主機上產備份，下載完立刻從外掛的 Backups 刪除，再 `curl -I` 驗回 404。
長期解法是請主機商加 nginx deny 規則，或備份改存遠端。接新主機時這條列進檢查。

### 主機剝掉 Authorization 標頭：應用程式密碼從外部一律 `rest_not_logged_in`

**症狀**：使用者產了應用程式密碼，從外部 `curl` 打 REST 一律 `rest_not_logged_in`；
**故意填錯帳密也回同一個訊息**——這就是確診：不是密碼錯，是主機（nginx／PHP-FPM 設定）
根本沒把 `Authorization` 標頭轉給 PHP。

**處置**：不要再換姿勢試憑證。改走**瀏覽器登入態**：請使用者在瀏覽器登入後台，
頁面裡 `fetch('/wp-admin/admin-ajax.php?action=rest-nonce')` 取 nonce，之後帶
`X-WP-Nonce` 打 `/wp-json/wp/v2/*` 讀寫（私密文章要加 `status=private,draft`）。
要把本機檔案傳進媒體庫：本機起一個帶 CORS 標頭的 localhost 靜態伺服器，頁面 JS fetch
取 blob 後 FormData POST `/wp-json/wp/v2/media`（可帶 `alt_text`、`post`）。
大批次注意瀏覽器工具的 JS 執行逾時（約 45 秒）：結果寫進 `window.__x`，逾時後再回來輪詢。
全程不經手任何帳密。

### ACF 欄位群組「Sync available (N)」是純讀 acf-json 的常態，不要按

正式站的 ACF 欄位群組頁顯示「全部 (0)」加「Sync available (24)」——代表資料庫 0 筆、
24 組全部從 `acf-json/` 載入，這正是 `docs/02-ACF規範.md` 三層分離要的狀態：
**改 acf-json 部署即生效**。按下「同步」會把 24 組匯入資料庫變成兩份，之後後台改欄位
會寫進 DB、正式站 acf-json 不可寫就分岔。清單全空時 ACF 會藏起「同步」分頁，也是正常的。

### 登入態限定的破版：admin bar 分三段，訪客看不到所以不用清快取

**症狀**：使用者（登入狀態）手機看文章頁，吸頂 header 懸在 46px 處、抽屜蓋住 header 上緣；
你未登入測怎麼都重現不了。

**成因**：核心 `admin-bar.css` 在 ≤600px 把 `#wpadminbar` 改成 `position:absolute`
（跟頁面一起捲走）、601–782px 高 46px、≥783px 高 32px。任何「為 admin bar 讓位」
的 CSS（吸頂 header 的 `top`、fixed 抽屜的 `inset`）都要對這三段分別處理，
≤600px 的讓位值必須是 0。

**處置**：這種 bug 只有登入者遇到，**不用清頁面快取**（登入者不走快取）。
AI 拿不到登入狀態時，在瀏覽器切手機尺寸後注入 `body.admin-bar`＋`html{margin-top:46px}`
＋一個 46px 高的 absolute 假 bar 就能重現；判斷位置用 `getBoundingClientRect()` 數字，
不要信 resize 後的第一張截圖（會拿到過渡狀態）。抽屜的解法是開啟當下量 header 實際下緣
寫 inline `top`，不是再堆 media query。

### 用 REST 建文章要用區塊標記，不要塞原始 HTML

用 REST 匯入／建立文章時，`content` 若是原始 HTML，整篇在編輯器裡會變成一個
「傳統編輯器」區塊，客戶要逐篇手動按「轉換成區塊」——批次搬 25 篇就是 25 次。

**處置**：產生 Gutenberg 區塊標記：`<!-- wp:paragraph -->`、`<!-- wp:heading {"level":3} -->`
（class `wp-block-heading`）、`<!-- wp:list -->`＋`<!-- wp:list-item -->`（class `wp-block-list`、
巢狀遞迴）、`<!-- wp:image {"id":N} -->`（figure `wp-block-image`、img 帶 `wp-image-{id}`）。
完成後在編輯器用 `wp.data.select('core/block-editor').getBlocks()` 檢查每個區塊 `isValid`。
主題不用 Gutenberg 排版（見 `AGENTS.md`）跟「客戶的文章內容是區塊編輯器寫的」是兩件事，
文章內容照 WordPress 的規矩來。

## 第二節：驗證的紀律

**共同主題一句話：這裡每一條的失敗，看起來都跟成功一模一樣。**

第一節的坑，出事的時候多半有某種可觀察的異常（畫面壞了、連不上、檔案不見）。
這一節的坑不一樣——**驗證跑完顯示通過，但實際上該測的東西根本沒被測到**，這種
失敗不會主動告訴你哪裡不對，只會安靜地放行一個有問題的結果。

### 切版完成的定義：頁面對 ≠ 完成

實例：某個頁面早就切版完成、上線，頁面本身完全正確——但它的 footer 連結卻一直
指向 `#`（佔位符，從未接上真正的網址）。這個問題存在了很長一段時間都沒被發現，
即使這個頁面通過了每一項既有的驗收：PHP 語法檢查（`php -l`）過、六種寬度的版面
量測全部 PASS、`curl` 回 HTTP 200。

**但站上沒有任何一個地方連得到這個頁面。**

根因：所有既有的驗收項目問的都是「這一頁本身對不對」（語法對不對、版面對不對、
伺服器有沒有回應），沒有一項驗收在問「**站台走得到這一頁嗎**」——也就是「使用者
從首頁、從選單、從任何一個入口，實際點得到這個頁面嗎」。頁面本身完美無瑕，
但它是一座孤島。

**推論**：驗收清單不能只驗證「產出物本身」，還要驗證「產出物跟系統其他部分的連結
關係」。切一個新頁面，除了頁面本身要過檢查，還要確認至少有一條使用者能實際走到
的路徑（選單項目、內頁連結、麵包屑）指向它，缺了這一項，頁面做得再完美也等於不存在。

### 量測回報通過 ≠ 通過

自動化的版面寬度量測（例如檢查頁面在六種標準寬度下有沒有產生水平捲軸）全部回報
PASS，但實際上版面有問題，至少發生過兩種模式：

1. **元素級溢出**：整個頁面的捲動寬度沒有超標，但頁面裡某個特定元素自己超出容器、
   視覺上明顯跑版。量測工具通常用整個文件的 `scrollWidth` 判斷有沒有水平捲軸，
   這個判準測不到「元素被裁切或框架吸收了溢出，但視覺上仍然有問題」的情況（例如
   父層容器設定了 `overflow` 裁切，子元素撐出的部分被悄悄吃掉、量不到捲軸，
   但畫面上內容看起來就是被硬生生切斷）。
2. **整段內容漏放**：模板裡漏掉一整段應該出現的內容（例如漏掉一個 `<p>` 標籤包住的
   提示文字），這種缺漏**既不會讓頁面變寬，也不會讓 `scrollWidth` 對不上**——
   量測工具檢查的是「有沒有水平捲動」，跟「內容對不對、齊不齊全」是兩件完全不同的事。

**推論**：量測工具只管「有沒有水平捲動」這一件事，不管「內容對不對」。內容是否
完整、正確，只能拿實作結果跟設計稿做截圖比對，逐區塊核對，沒有替代的自動化捷徑。
兩種驗證方式要一起用，缺一種都會漏掉另一種能抓到的問題類型。

### DPR 1 和 2 都乾淨，不代表沒事：非整數倍率會露 1px 縫

**症狀**：使用者回報畫面上有一條淡淡的直線（或細縫），你在 headless 的
DPR 1 與 DPR 2 掃了多個視窗寬度都重現不了，差點歸類成「使用者環境問題」。

**成因**：兩個貼齊定位的元素（例如照片跟蓋在上面的漸層遮罩，同一個 left 值）
在整數 DPR 下捨入結果一致、貼得天衣無縫；在**非整數 DPR（1.5——4K 螢幕開
150% 縮放，非常常見）**下，兩個元素各自的子像素捨入可能差 1 個裝置像素，
下層元素就露出一條 1px 的邊。

**處置**：①版面掃描的矩陣要把 `deviceScaleFactor: 1.5` 加進去（Playwright
一行設定的事）；②修法是把覆蓋層朝縫的方向**多蓋 2px**——遮罩邊緣通常是
純色或全透明，多蓋沒有視覺差異，但把兩邊的捨入誤差都吃掉了。

### 只有 Safari 壞的 bug，用 Playwright WebKit 重現，不用裝 Xcode

**症狀**：使用者回報手機 Safari 有問題，你手上只有 Chromium 系工具，怎麼掃
都重現不了；iOS 模擬器那條路又需要完整版 Xcode（十幾 GB，多數開發機只有
command-line tools）。

**處置**：Playwright 的 WebKit 是真的 WebKit 引擎，約 83MB 一分鐘裝完：
`node <playwright-core 路徑>/cli.js install webkit`，之後
`require('playwright-core').webkit.launch()` 配 iPhone 的 viewport／UA／
`hasTouch` 就是可程式化的行動版 Safari。實測 Chromium 完全重現不了的
「捲到底看不到 footer」在 WebKit 一次重現，並靠它定位到成因與驗證修復。
**「只有 Safari 壞」的回報進來，先架 WebKit 再開始猜**，猜的每一輪都比
裝它貴。

### 「數字串出現幾次」的檢查會失準

驗收「這段程式碼有沒有重用既有元件、不是重新切了一份」，直覺的做法是用
`grep -c` 之類的指令，去數某個元件名稱的字串在呼叫端程式碼裡出現了幾次。

**這個檢查隱含一個假設**：重用的痕跡會以「字面字串」的形式出現在被檢查的程式碼裡。
但如果實際寫法是用迴圈動態組出要 include 的檔名（例如把一組識別字放進陣列，
`foreach` 迴圈裡動態組字串去 `include`），元件的名稱字面上只出現在**被引入的那個
檔案本體**裡，不會出現在呼叫端的原始碼字面上——這種寫法下，`grep` 對呼叫端的
命中次數是 **0**，但實際上重用確實發生了。

**0 次不代表沒重用，代表 grep 挑的字串跟這段程式碼的抽象層級不對。**

**通則：任何「數某個字串出現幾次」的驗收檢查，先確認寫法本身會不會讓那個字串
以字面形式出現。** 動態組字串（變數、迴圈、字串格式化函式）幾乎必然會讓這類
`grep` 檢查失準——遇到這種寫法，要驗證重用有沒有發生，得追進被引入的那個檔案
本體去找函式名、class 名，並確認那個檔案在這次改動期間沒有被複製出另一份、
內容真的沒變過（改過就是掛羊頭賣狗肉的假重用；沒改過才是真重用）。

### 行號引用會漂移

跨 session、跨 agent 交接工作時，如果指位置只用行號（「看 `xxx.php` 第 230 行」），
一旦上游檔案在那之前被任何人編輯過、增減了幾行，**行號會整組錯位**，指到完全不同
的內容，而且不會有任何錯誤訊息告訴你指錯了。

**基本對策**：改用 class 名、函式名、註解裡的關鍵字，或用 `grep` 得到的具體字串
當定位依據，行號只能當輔助參考，不能單獨依賴。

**續篇，也是更重要的一條**：光是「改用 class 名定位」解決不了全部問題，真正的
問題不是「行號會漂移」，而是「**檢查範圍圈太小**」。實際發生過的情況是：一次改動
讓某個檔案整體增加了幾十行，導致該檔案後半段所有既有的行號引用（分散在另一份
文件裡，引用這個檔案很多處具體位置）全部同時失效。派工時如果只交代「驗證你新增
的引用」，執行者會忠實地把新增的引用都驗過、都是對的——**但舊引用完全不在任何人
的檢查範圍內，於是沒有人發現整份引用文件已經過期**。其中还有部分是「裸行號」
（只寫數字，沒有帶檔名前綴），連用正則去掃都掃不到，只能逐段閱讀才發現。

**通則：凡是改動了「被其他文件用行號引用」的檔案，要核對的是那份文件裡全部的
引用，不是只核對這次改動新增或碰過的部分。** 把檢查範圍限定在「自己的改動」，
對「自己的改動害別人的引用失效」這個方向是完全盲目的。

### 早退分支要留可分辨的 log

開發過程中常見一種難以定位的症狀：「頁面看起來沒套到樣式，但沒有任何地方會告訴你
為什麼」。程式邏輯裡如果有多個提前返回、提前跳出的分支（某個條件不滿足就直接
`return`、不繼續往下執行），而這些分支彼此之間、跟正常執行路徑之間，輸出看起來
可能一樣「沒有東西顯示」，排查時完全無從分辨到底是走了哪一條路才停下來。

**規則：開發環境下，每一個提前返回的分支都要各自寫一行可分辨的訊息**（可以是
`error_log`，也可以是任何開發環境才會啟用的除錯輸出），讓排查者一看就知道「這次
是在哪個判斷點被擋下來的」，而不是要逐一在程式碼裡插斷點才能分辨。

> **適用範圍**：這條講的是「同一個症狀可能來自好幾個不同判斷點」時，除錯用的
> log 該怎麼寫——多個早退分支彼此無法區分才需要這條。**不適用於**
> `docs/01-切版SOP.md`「沒資料就 `return`，整區不輸出」那種版型 partial：
> 那類早退只有一種「沒資料」的原因、輸出也刻意設計成「什麼都不印」，加 log
> 反而會在正式環境噴出雜訊。示範 partial（`template-parts/section-hero.php`、
> `template-parts/section-cards-3col.php`）維持裸 `return` 是刻意的，不是漏做。

### 白名單過嚴會安靜擋掉合法輸入

驗證或過濾機制如果用白名單（只允許清單裡列出的字元、格式、名稱），白名單本身
如果漏考慮了一種合法情況（例如漏掉底線這種常見的合法字元），會產生「合法輸入
被悄悄擋掉，沒有任何錯誤訊息」的結果——檔名被拒絕、CSS 悄悄沒被掛上，表面上
系統運作正常（沒有跳錯誤），但預期的行為就是沒有發生。

這類坑特別難查，因為**沒有失敗訊息可以追蹤**，唯一的線索是「預期該發生的事沒有
發生」。寫白名單機制時，先列出所有合法輸入的實際樣式，逐一核對白名單真的涵蓋，
不要憑印象覺得「應該夠了」。

### 煙霧測試標記漏掛是安靜的

用某個 class 名稱或標記字串是否出現，當作簡易的煙霧測試（smoke test）去驗證
某個功能有沒有生效，是常見的低成本驗收手段。但如果程式改動時漏掉了把這個標記
掛上去的那一步，**煙霧測試不會讓頁面壞掉，只會讓計數悄悄從某個數字變成 0**——
頁面外觀可能完全正常，只是少了那個原本該存在的標記。如果沒有人盯著這個計數本身，
這種漏掛可以在系統裡潛伏很久都不被發現。

### 這次做起案包時踩到的五個假檢查

把上面的通則具體化：以下是實際建這個起案包過程中，親身踩到的五個「檢查沒報錯，
但檢查本身失效了」的案例，全部來自 macOS 的 BSD 工具鏈跟 GNU 工具鏈的行為差異
（或工具被包裝過導致行為不穩定）：

| 工具／做法 | 問題 | 改用 |
|---|---|---|
| `awk`（macOS 內建是 one true awk） | `{n,m}` 這種數量詞、`\b` 這種詞界符號都**不支援，而且不會報錯**，正則悄悄退化成別的意思 | 改用逐位元展開的 pattern（把 `{n,m}` 展開成對應個數的重複寫法） |
| `sed`（macOS 內建是 BSD sed） | `\b` 不支援，同樣不報錯 | 改用 `[[:<:]]` / `[[:>:]]`（BSD 的詞界寫法） |
| `grep`（這台機器的 `grep` 是被包裝過的 shell 函式） | 當它是管線的第二段（接在別的指令後面）時，行為不穩定 | 過濾用途的那一段一律寫 `command grep`，繞過包裝直接呼叫真正的 grep |
| 用 `global $menu` 檢查 ACF 設定頁選單有沒有註冊 | 在 wp-cli（命令列）環境下執行時，這個全域變數永遠是空的——不是設定頁沒註冊，是**檢查的方式本身在這個執行環境下量不到東西** | 改用 `acf_get_options_pages()` 這個 ACF 提供的函式呼叫，不依賴只有網頁請求週期才會被填值的全域變數 |
| `grep -c 'commit'` 檢查某份文件有沒有記到一個 commit hash | 那一行文字裡字面上本來就寫著「commit」這個詞（例如「這裡要記 commit hash」這句提示文字本身），檢查**永遠回傳至少 1**，不管有沒有真的填上 hash | 改成驗證後面接的字串符不符合十六進位雜湊值的格式，而不是只數關鍵字出現次數 |

另外再加一條相關但獨立的教訓：**底線（`_`）在 POSIX 正則裡算是「詞字元」的一部分**，
所以拿詞界（word boundary）去比對像 `field_st_x` 這種變數名裡的 `st_`，抓不到——
因為 `_` 跟 `s`、`t` 一樣都算詞字元，`st_` 前後沒有真正的詞界。**這不是 BSD 工具鏈
獨有的行為，換成 GNU sed 一樣抓不到**，因為這是 POSIX 正則對「詞字元」的定義本身
造成的，不是哪個工具實作得不好。要抓這種帶底線的識別字片段，得直接寫出完整的替換
pattern（例如 `s/_舊前綴_/_新前綴_/g`），不要依賴詞界符號。

**這五個案例共同的教訓**：**寫完一個檢查，先故意製造它應該要抓到的錯誤情況，
確認它真的會回報失敗，再拿去驗真正的東西。** 上面每一個案例，如果當初有做過這一步
負向測試，都能在第一時間發現檢查本身失效，不必等到後來才發現「原來一直都沒真的
測到東西」。

> 任何驗證工具，用它之前先想一次「它失敗的時候會長什麼樣子」。
> 如果答案是「跟成功一樣」，它就不能單獨當作通過的依據。

### 負向測試的探針，要放在「真實內容會出現的位置」

「先故意製造它該抓到的錯」這條紀律，本身也有一種會失效的方式：**探針放錯位置**。

實案：驗證一支「頁面寬度量測工具」有沒有效，把一個 1800px 寬的探針元素插進頁面、
工具回報抓到了，於是宣告「工具有效」——但探針被插在頁面最外層，而**真實內容全都
包在一個 `overflow-x: clip` 的容器裡面**，容器裡的溢出被 clip 吃掉、`scrollWidth`
完全反映不出來。也就是說：工具只測得到「容器外面」的溢出，而真實內容永遠在
容器裡面——負向測試驗到的是一個**不會發生的情境**，工具對真正會發生的失敗
其實是瞎的。

**負向測試要模擬真實的失敗**：探針放進真實內容所在的容器裡、用實際會出現的
寫法去觸發，然後才看檢查有沒有抓到。探針在「不會有內容的位置」被抓到，
不構成任何證明。

順帶記一條走不通的修法：想消「有祖先在裁切」造成的量測假陽性，**不要用
「有祖先在裁切就自動排除該元素」**這條規則——當那個裁切容器本身就是全頁內容的
共同祖先時，這條規則會把每一個元素（連探針）都排除掉，等於永遠回報通過。

### 審共用 pattern 的改動，第一步列出全部 include 點；交審訊息的數字不能信

**症狀**：改碼方自報「這個 pattern 有八頁在用」「這個欄位只輸出在三處」，審查照著
八頁、三處驗，全過。事後發現第九頁、第四處漏了——剛好行為是預設所以沒出錯，
但文件寫錯了；另一次是地址改成連結，漏掉的那處在團隊頁，客戶點了落點不對。

**成因**：數字是改的人自己數的。迴圈裡 include 的頁（`foreach (['a','b']) include`）
只有 grep **檔名**才看得到；欄位名與字面值分兩種寫法，只搜其中一種就漏。

**處置**：審任何共用 pattern／partial／欄位的改動，第一步固定
`grep -rn '<檔名或欄位名>' --include='*.php'` 列出所有消費者，**欄位名與字面值都搜**
（`clinic_address` 與地址文字各搜一次），逐頁實抓，不接受「其餘 N 頁」這種數字。
驗法：對每一頁算「畫面上可見的目標字串次數」與「包在預期標籤裡的次數」，兩個數字要相等。
（同根源：上方「數字串出現幾次的檢查會失準」。）

### 本機站是改碼與審查共用的量測對象：先比 md5，被蓋掉就攔截樣式檔量「某個 commit」

**症狀**：審查 commit A 時，WebKit 那輪量到 A、Chromium 那輪量到的卻是「三張一組變兩欄
且少一張」——看起來像 A 壞了，第一直覺是引擎差異。實際上改碼方在審查中途把下一筆
未提交的 style.css cp 到了本機站。

**處置**：
1. 每輪量測**前後各比一次** `md5 -q <本機站/style.css>` 與 `git show HEAD:style.css | md5 -q`，
   再看 `git status`，一分鐘排除。
2. 審查方唯讀、不能把本機站改回去（會蓋掉對方的半成品）。不動本機站的重量法：
   `git show <hash>:style.css > scratchpad/x.css`，Playwright 腳本 `browser.newContext()` 後
   `context.route(/\/themes\/<主題>\/style\.css(\?.*)?$/, r => r.fulfill({status:200,
   contentType:'text/css', body:CSS}))`，再 `newPage()`／`goto()`，**計數攔截次數**確認每頁都換到。
   前後各量一輪就是改前改後對照。
3. 約定：上一筆審查結論回來前，改碼方不 cp 下一筆到本機站；非先 cp 不可就先發訊息。
   cp 到本機後第一次抓可能還是舊程式（opcache），先暖機再量。

### 本機與正式站同一頁的 HTML 結構可能不同

**症狀**：「依內容結構判定」的修法（例如正則判斷 `<p>` 內是否全部包在 `<strong>` 裡才加 class）
在本機 19 個邊界案例全過，正式站第一段卻是另一種巢狀順序
（`<strong><a>…</a></strong>` vs `<a><strong>…</strong></a>`）。

**成因**：客戶在正式站改過內容，本機同步時只同步了文章（post）沒同步頁面（page）。
本機從來不是正式站的鏡像，只是「大致相同」。

**處置**：凡是依內容結構判定的程式，要**對正式站抓下來的 HTML 另跑一次**，不能只在本機驗。
量測工具只能對本機跑時，交審前先比對正式站的資料分布（篇數、分類掛法）跟本機是不是同一回事。

### 繞快取的參數不要用 `?m=`；驗正式站先確認不是 404 頁

兩個審查方實際犯過的誤判：

- 想繞頁面快取加了 `?m=<時間戳>`——`m` 是 WP 的月份查詢變數，整頁 404，
  然後把 404 當成「碼沒上去」。用 `?nc=<時間戳>` 這種 WP 不認的名字。
- 抓 `/clinic-info/`（根本不存在的網址）看到 404 頁上的共用區塊，就回報「門診資訊頁已改好」。
  **404 頁上也有 header／footer／pattern**，先看 `<title>` 或狀態碼確認抓到的是目標頁。

### 純函式的邊界測試：擷取函式 `eval`、stub 掉 WP 函式，不用起整個 WordPress

要驗一支純字串處理函式（例如依正則給 `<p>` 加 class）的 19 個邊界案例，不用啟動
WordPress：從 `functions.php` 擷取該函式區塊 `eval`、把它呼叫到的 WP 函式
（`wp_strip_all_tags` 之類）stub 成最小實作，用 Local 的 php CLI 直接跑案例、印結果比對。
比在網站目錄放測試檔乾淨，也不用開瀏覽器。

要跑**需要 WordPress 環境**的函式（撈文章、渲染卡片）則是另一條路：Local 的 php CLI
帶 `-d mysqli.default_socket=<socket>` 載 `wp-load.php`，腳本開頭設 `$_SERVER['HTTP_HOST']`，
之後任何主題函式都能呼叫、輸出存檔做「改前改後 `===` 比對」。**腳本放 scratchpad**，
不寫進網站目錄（會被權限擋、或被 deploy 打包）。

⚠️ shell heredoc 寫含 `$` 的 PHP 一定要 `<<'EOF'`（單引號），否則變數被 shell 吃掉、
網站直接 500。

### 客戶的舊裝置回報：先查系統版本，不是每台都該相容

「某台 iPad 圖片出不來、排版跑掉」——先問機型與系統版本。iOS 12 的第一代 iPad Air
不支援 WebP（要 iOS 14），flex gap／`clamp()`／`aspect-ratio` 要 iOS 13.4–15。
這是裝置過舊，不是 bug；主題要不要為它做相容是**裁定**，不是排查。
（反例見 `docs/03-樣式與設計系統.md` 第七節：iOS 16 的舊 iPhone 還在客戶群裡，
`@container` 就不能用。）

### scratchpad 跨日會被清空：證據寫進 HANDOFF 或 repo docs

審查 session 當天存在 scratchpad 的截圖、量測腳本、部署包，隔天全部消失。
要留的證據（部署前後截圖、量測數字）寫進 `HANDOFF.md` 或 repo 的 docs；
腳本重寫就沿用 `tools/_webkit-lib.mjs`——`import 'playwright'` 在 scratchpad 解析不到，
要從 lib 拿 `launch`，或符號連結 `tools/node_modules`。

### 相鄰垂直外距會合併：承諾「會看到 N px 變化」前先算

**症狀**：審查報告寫「正式站警語會從 0 變 9.6px」，部署前後截圖 diff 做出來是 0 差異，
差點以為 CSS 沒生效。

**成因**：警語 `margin-top:.6em`（9.6px）前面的清單有 `margin-bottom:.7em`（11.2px），
相鄰垂直外距取大者，修法正確但在這個位置看不到。

**處置**：修 margin 類的改動，交審／驗收時先算會不會被相鄰外距合併吃掉，
把「在什麼情境下才看得到」寫進報告，不要承諾一個不會出現的數字。

### 真元件要對齊舊圖烤進去的位置，用亮點法量，不要目測

**症狀**：Banner 底圖裡原本烤著一排圓點，改成真元件後要「重合」。改碼方目測間距 3px，
實際是圓心距 1.25vw——差一倍，1440 寬時第一顆錯開 7px，肉眼可見雙影。

**處置**：用 canvas 取圖 → 亮度門檻 → 連通元件 → 算每個圓心座標，再換算成 vw 公式
（點徑、圓心距、離底距各一個 vw 值）；手機圖另外量一組。設計師輸出的 2x 圖本身
就是最準的設計稿。commit 訊息寫「重合」要附量法，審查要自己量才算驗過。

### 固定在視窗底的元素會蓋住 fixed 容器的內容；Playwright 的 `env()` 永遠是 0

**症狀**：手機抽屜捲到底，最後一顆 CTA 被底部快捷列蓋住 26px；模擬器量到「只差 3px」。

**成因**：抽屜 `padding-bottom:48px` 只是巧合比快捷列 40px 高 8；有 Home 指示條的 iPhone
快捷列實際 74px 高（40＋34 安全區）。Playwright 的 `env(safe-area-inset-bottom)` 永遠回 0，
量不到這一截，實機其實差一整截。

**處置**：寫法見 `docs/03-樣式與設計系統.md` 第七節；驗法是 `page.addStyleTag` 把相關規則
的 `env()` 暫換成 `34px !important` 再量一次，交審附「暫換 34px」的對照數字。

## 第三節：多人／多 agent 平行作業

這節現有的任何文件都沒寫過，但只要專案不只一個人（或一個 agent）在同時動，
遲早會遇到這裡列的情況。

### 平行化會放大規範缺漏的代價

兩個互不知情的 agent 各自獨立寫出「同一種沒有防護的寫法」，各自踩到同一個坑——
不是巧合，而是因為那條防護規則**存在於程式碼庫既有的其他元件裡，卻不存在於任何
文件**。單一 agent 循序做事，這類坑最多踩一次（踩到之後學到教訓，後面不會再犯）；
但兩個 agent 同時平行做同一類任務，同一個缺漏會被**平行踩兩次**——因為兩邊都沒有
機會從對方的經驗裡學到東西，各自獨立重蹈覆轍。

**反證也成立**：把這類教訓明確寫進派工封包（brief）之後，下一輪平行作業裡，
其中一份工作**一次通過、零 Critical 問題**——規則存在於文件裡跟存在於程式碼裡，
對「會不會被平行踩兩次」有實質差異。

**推論**：任何只存在於「資深工程師腦中」或「散落在某個元件實作細節裡」的防護規則，
一旦要開始平行派工，第一件事就是把它寫進共用的規範文件，不要假設每個 agent 都會
自己從既有程式碼裡歸納出同一條規則。

### 派工單寫的「已知結構」準確率很低

實測過三個 agent 平行接派工單，**全部都修正了控制端寫的「已知結構」描述**：
漏掉整個應該存在的區塊、把某種圖表類型寫錯成另一種、區塊的先後順序寫反。
最嚴重的一次是：派工封包聲稱某個檔案裡有一段可以參考的既有實作，執行的 agent
讀完整份檔案（數百行）之後才確認——**那段實作根本不存在，它只出現在設計稿裡**，
從未被真的寫進程式碼。

根源通常是：控制端撰寫派工封包時，對「已知結構」的描述其實來自對設計工具（例如
設計稿檔案的節點結構、座標）的**推斷**，不是對程式碼本身的**確認**。設計稿裡的
節點名稱如果是自動產生的流水號（沒有語意的命名），推斷出來的結構描述本質上是猜測，
猜錯的機率不低。

**規則：派工單要標明清楚哪些描述是「親眼確認過」（讀過程式碼、跑過指令驗證），
哪些是「推斷」（從設計稿節點、命名慣例、間接證據猜出來的）。** 引用任何「既有實作
可以參考」之類的說法之前，先確認那個實作真的存在，不要假設封包寫的就是事實。
執行者收到派工單時，也應該對「已知結構」保持懷疑，發現跟實際不符要主動回報並修正，
不要因為封包這樣寫就照單全收。

### 拆檔是為了避開無聲覆寫

多個 agent（或多個人）同時對同一個大檔案做追加式修改，會發生一種特別隱蔽的失敗
模式：**寫入回報成功，但內容被另一個幾乎同時發生的寫入覆蓋掉**——因為兩邊都是
基於「寫入前讀到的舊版本」去組出新內容再整份寫回，後寫入的那次會把先寫入的那次
覆蓋掉，兩邊都不會收到任何錯誤或警告。

**規則**：拆分工作範圍時，讓每個 agent 各自負責獨立的檔案，彼此不重疊（例如
「一頁一檔」，各頁各自的模板檔與樣式檔互不相干）。真的需要共用的入口（例如一份
彙整所有頁面連結的清單檔），改由**單一序列**維護——同一時間只有一個寫入者，
不讓多個平行的寫入者同時競爭同一份檔案。

### 三條實測有效的平行規則

實際跑過多輪平行派工（agent 數從 2 增加到 3，沒有出現新的衝突類型），歸納出三條
確實有效、可以直接沿用的規則：

1. **agent 不碰 git。** 多個 agent 同時執行 git 操作，`.git/index.lock` 會互相
   衝突。改由控制端在每個 agent 各自回報完成之後，**分別各自 commit**——git 操作
   全程只有控制端在跑，避免多個行程同時碰同一個 git 倉庫的鎖檔。
2. **除錯用的連線埠（例如瀏覽器自動化的 CDP port）要分流。** 不同 agent、以及控制端
   自己的驗證流程，各自用不同的埠號（例如慣例上一個埠給 subagent 用、另一個埠留給
   控制端）。不分流的話，後啟動的那一方發出的導航指令會把前一個還在使用中的頁面
   導航掉，兩邊互相干擾彼此的驗證結果。
3. **素材檔名前綴分流。** 每個 agent 負責的範圍各自用不同的檔名前綴（例如依頁面或
   模組命名），避免同時上傳/產生素材時互相覆蓋或搞混。實測過 31 個檔案、三種前綴
   全部零撞名。

這三條規則在 agent 數量增加時沒有暴露出新的衝突類型——代表它們解決的是平行作業
本身結構性的競爭問題（版控鎖檔、網路埠佔用、檔名空間），跟平行的規模無關，是可以
直接沿用的基礎規則，不需要每次增加 agent 數量都重新設計一套新機制。

### 多條工作線同時動同一個 repo 是常態，不是例外

上面講的是「一個控制端派多個 agent」；這條講的是另一種更隱蔽的並行——**多個
互不知情的工作階段**（不同的人、不同的 session、不同的電腦）同時在動同一個
repo。實測發現同一天同一個 repo 上有三條線同時在跑，彼此都不知道對方存在；
連兩條線互相通知時，**雙方都誤判了對方是誰**——A 以為某批 commit 是 B 做的、
B 查了 git log 才發現不是自己。

實測歸納的紀律：

- **判斷某個 commit 是誰做的，查 `git log --format='%an %ae'`，不要憑印象。**
- **對方宣稱「已完成」的工作，驗證實際狀態再依賴它。** 實測過文件註解寫
  「兩個區塊都接好了」，但其中一區的 markup 根本沒改——靠前台渲染結果逐一
  數元素才抓到。文件說做了不等於程式碼真的改了。
- **改動 commit hash 的操作（amend、rebase）要主動告知其他線**，否則對方的
  紀錄會指向一個不存在的 commit。
- **風險最高的交會點是部署**：鏡像部署會把「本機清單沒有的遠端檔」刪掉，
  兩條線在不同的 `main` 狀態下各自部署，後部署的會把前一條的東西當成遠端多餘
  而刪掉。完整紀律見 `docs/04-部署SOP.md`「多條工作線並行」一節。

### 多 session 共用 git index：commit 會把「別人 staged 的東西」整包收走

同一天三條線互相誤收對方 staged 的改動，共通成因：**`git add <自己的檔>` 之後
commit 的是整個 index**，別的 session 先 stage 的內容會一起進去。更陰的是鏈式指令
`git status && git add && git commit`——status 印出了別人的 staged 列，但鏈不會停，
等於看了也白看。

**紀律**：
1. commit 前**單獨**跑 `git status --short`，看完 staged 欄（第一欄字母）再決定——
   有不是自己的 staged 內容，不要直接 commit。
2. 只想提交自己的改動時用 index 手術：`git show HEAD:<檔>` 重建「HEAD＋自己的 hunk」版
   → `git hash-object -w` → `git update-index --cacheinfo` → commit → 把對方的 staged 狀態
   `git add` 回去。整套不動工作區、不動對方內容。
3. 誤收後兩種補救：沒 push 前 `git reset --soft HEAD~1` 拆掉重做；已有後續 commit 疊上去
   就補一個 note commit 註記。
4. **staged 不過夜**：`git rm`／`git add` 完盡快 commit，中間不要插長流程——staged 狀態
   掛在共用 index 上就是給隊友挖的坑。

### commit 與 `./deploy.sh` 不要串在同一條指令鏈

把 `php -l && git commit && ./deploy.sh` 串成一條鏈執行：commit 前的 `git status` 雖然
印出「工作樹多了別線 3 個未 commit 的檔」，但鏈不會停、人眼還沒看到輸出部署就跑完了——
別線的半成品被鏡像部署直接端上線（那次運氣好，數秒後對方 commit 的內容與已上線檔案一致）。

**紀律**：`./deploy.sh` 永遠**單獨一條指令**執行，執行前的 `git status` 輸出要「看過再按」，
不是「有跑過就好」。多 session 常態下，工作樹在你 commit 和你部署之間的幾秒內都可能
長出別線的 WIP。deploy.sh 的第 0 步（工作目錄不乾淨就中止）是配套，不是替代。

### 事後判讀「檔案早就被刪」vs「被並行線夾帶」：看那個 commit 的時間

你 `git rm` 了一個檔、還沒 commit 的空檔裡，另一條線在同一個工作樹 `git commit`——
你的 staged 刪除被夾帶進別人的 commit。等你要 commit 時，三個證據拼起來活像
「這檔早就被移出 git」：`git status` 沒有 staged D、HEAD 沒有這個檔、
`git log --diff-filter=D` 指向一個標題完全無關的 commit。

**正確判讀**：先看那個 commit 的時間 `git log --format=%ci -1 <hash>`——是「幾分鐘前」
就是並行線夾帶，不是歷史遺留；再對照該線的 HANDOFF／commit 訊息。
當下差點把錯的推論寫成教訓，是靠時間戳擋下來的。

### 協作 session 的名字可能當天中途改：先重新 ListAgents，不要當對方掉線

改碼 session 開頭叫「<自動產生的標題>」，中途被使用者改成「寫碼1008」，ref 沒變。
第一次 SendMessage 成功、第二次回「No agent named …」，差別只是名字。
**處置**：回 No agent named 先重新 `ListAgents` 用新名字送，不要判斷成對方離線。
同理，審查 session 也是按日期新開、名字每天不同——交審前先 ListAgents、以使用者當天
指定的為準，不要憑記憶裡的名字直接傳；新舊 session 可能同時在線，只傳給被指定的那個。
