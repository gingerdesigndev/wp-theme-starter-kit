## 第一節：環境與工具

### 症狀對照表

先查這張表，看你眼前的怪現象對得上哪一列：

| 你看到 | 其實是 | 怎麼辦 |
|---|---|---|
| 改了 PHP 但沒反應 | opcache 餵舊碼 | `kill -USR2 "$(pgrep -f 'php-fpm: master' | head -1)"` |
| header 在截圖裡不見 | headless 截圖騙人 | 開真實瀏覽器確認再說 |
| header 在真實瀏覽器也不見 | 頁面建構器的 Theme Builder 蓋掉了主題的 header/footer | 見下方「頁面建構器吞掉 header/footer」一條 |

| 熱門文章排序長期不動、瀏覽數低得離譜 | 瀏覽數外掛被整頁快取架空 | 見下方「瀏覽數統計外掛」一條 |
| 圖片比例跑掉、構圖被裁得很怪 | `width:100%`+`aspect-ratio` 沒補 `height:auto`，aspect-ratio 整條失效 | 見 `docs/01-切版SOP.md`「寫 template-part」必守細節 |

以下逐條展開成因與處置。

### opcache 餵舊碼

改了 PHP 檔案，重新整理頁面卻看不到變化——不是你改錯地方，是 PHP 的 opcache 還在
餵編譯過的舊版本。開發環境常見（正式站與 Local 都會遇到，一次性驗證用的伺服器如果
沒有持久化 opcache 則不會，但不要假設自己的環境是哪一種，遇到就先重載一次）。

```bash
kill -USR2 "$(pgrep -f 'php-fpm: master' | head -1)"
```

這行對 php-fpm 的 master process 送 `USR2` 訊號，觸發優雅重啟，會清掉 opcache 與
realpath cache。**不重載你會開始修一個不存在的 bug**——反覆檢查程式碼、懷疑自己
邏輯寫錯，實際上程式碼從一開始就是對的，只是伺服器沒在跑它。

### headless 截圖騙人

用 headless Chrome（或任何無頭瀏覽器）截圖判斷版面，看到 header 憑空消失、
版面跑掉——**不代表真的壞了**。

成因：滿版元素（`width:100vw` 搭配負 margin 撐出視窗外）在 headless 環境的算繪，
某些設定下會依「視窗高度」而不是「視窗寬度」出錯，把畫面上半部的內容吃掉。
真實瀏覽器對同一份 HTML/CSS 完全正常渲染。

**鐵律：版面問題自己開真實瀏覽器視窗看，不要只信 headless 截圖下結論。**
`curl` 抓 HTML 比對結構（有沒有那個 DOM 節點）是可靠的輔助，但視覺判斷一律用真實
瀏覽器。

### headless 量不了窄視窗

用 headless Chrome 的 `--window-size=375,...` 想模擬手機版寬度截圖，拍出來的圖確實
標示 375 寬，但**畫面內容其實是用比 375 更寬的視窗排版後再裁切成 375 的**——結果是
右側被硬生生切掉，看起來像嚴重爆版，但那是假象。

原因是部分 headless Chrome 版本對 `--window-size` 有隱性下限（實測會被夾在 500px
附近），小於下限的設定不會真的生效，只是輸出圖片的尺寸被裁切成你要的數字。

**正確做法**：要精準模擬窄視窗（尤其 320～375px 這種手機寬度），改用 CDP 的
`Emulation.setDeviceMetricsOverride`，直接告訴瀏覽器「你現在的視窗就是這個寬度」，
而不是拍完整寬度的圖再裁切。

**驗證方法本身要先驗證**：暫時在頁面兩側各放一條 `position:fixed` 的窄色條，
拍出來的圖色條應該貼齊畫面邊緣；如果色條位置不對，代表你量到的不是真正的窄視窗版面。

### fail2ban

短時間內 SSH 連線失敗次數過多，會被主機的防護機制（fail2ban 或類似機制）暫時封鎖。

**症狀特徵**：`nc -z` 測 TCP port 是通的，但 SSH 一開始交換版本字串就被重置
（`kex_exchange_identification: Connection reset by peer`）——連線根本沒有進到
認證階段，所以跟金鑰對不對、帳號密碼全都無關。

**最容易踩的坑**：以為「等一下再試」是安全的處置。實際上**每一次失敗的連線嘗試，
本身就會把封鎖的倒數重新計算**。所以「等 15 分鐘 → 重試 → 又失敗 → 再等 15 分鐘」
是一個永遠出不去的迴圈——每次重試都在延長封鎖，不是在等它自然解除。

**正確解法**：到主機面板把 SSH 服務**停止、再啟動**。重啟服務（尤其容器化的主機）
通常會清掉封鎖狀態，這比等待可靠得多。完整的判定流程（怎麼分辨是 fail2ban、金鑰
問題、還是服務沒開）見 `docs/04-部署SOP.md` 第四節。

**衍生規則**：想預覽某個操作會動到遠端哪些檔案，用工具內建的 `--dry-run` 之類的
機制在同一次連線裡看完，**不要另外再開一條 SSH 去手動查**——每多開一條連線都會
再消耗一次失敗配額，累積起來就是被封鎖的那一根稻草。

### 頁面快取外掛

安裝了頁面快取外掛（WP Rocket、LiteSpeed Cache、W3 Total Cache 這類）的正式站，
把整頁 HTML 存成靜態檔直接餵給訪客，**改動 theme 檔案不會自動觸發清除快取**——
多數快取外掛只認「內容被更新」（文章、頁面被重新儲存），不認「主題檔案被換掉」。

**驗證陷阱**：帶 query string 的 `curl`（例如加 `?v=時間戳`）能繞過快取拿到即時版本，
會讓你誤以為「部署驗證通過」，但那只證明程式碼本身是對的，**不代表訪客實際看到的
是新版**。訪客請求的是裸網址，裸網址走的是快取。

**鐵律：驗證一定用裸網址**，不要加任何 query string。

快取外掛的清除粒度通常是**逐頁的**：改一個影響全站版型的東西（header、footer、
選單）之後，重新儲存單一頁面往往只清那一頁，其他已經被快取住的頁面仍然是舊版。
**改動若影響全站版型，要逐頁抽驗**，只驗首頁就宣告成功會漏掉內頁還沒更新這件事。

有些快取外掛的行為不對稱：**可能不快取 404 頁面，卻正常快取一般頁面**——如果你拿
一個 404 頁測「有沒有快取問題」，得到「立刻是新版」的結果，不代表其他一般頁面也是
新版，這兩種頁面的快取行為可能完全不同，不能用其中一種的結果去推論另一種。

### 選單存資料庫，footer 跟著主題部署

站上「看起來都是導覽」的東西，存放位置其實分兩種，部署行為完全不同：

- **後台選單**（外觀 → 選單）存在**資料庫**——不進 git、不隨主題部署，
  每個環境各自維護，改它要進後台（或走 REST），改完通常還要清快取。
- **footer / header 裡硬編在模板檔的連結**，隨主題檔案部署——`deploy.sh`
  跑完就是新的。

這個分野本身就是診斷線索：部署主題後「footer 的連結更新了、導覽列還是舊的」
**不是部署失敗**——footer 跟著檔案走所以變了，導覽列存在 DB、而且各頁快取住的
HTML 裡還是舊的 `href`。處置是改資料庫裡的選單＋清快取，不是回頭懷疑部署。

連帶一條：**選單項目的 db_id 在本機與正式站幾乎必然錯位**（兩邊各自建資料列、
各排各的編號，可能整組平移幾號）。照本機的 db_id 上正式站改選單，會改到
**別的項目**。驗收也有陷阱——用「某連結有沒有出現在 nav」驗收，對「改錯項目」
完全不敏感：改錯項目一樣會讓那個連結出現、一樣「通過」。正確驗法是按項目
**標題**對照：確認那個 db_id 的 title 是預期的項目、**且** url 也是對的，
兩者同時成立才算過。

### 瀏覽數統計外掛被整頁快取架空

多數瀏覽數外掛靠 PHP 在頁面渲染時累加計數——而被整頁快取住的請求**根本不執行
PHP**，於是瀏覽數長期嚴重低估、熱門排序幾乎不動，而且沒有任何錯誤訊息。
裝了整頁快取外掛的站（多數正式站都有）要用瀏覽數外掛，**計數模式必須改成
JS／AJAX 類**（外掛通常有 `js`、`rest_api`、`fast_ajax` 這類選項），讓計數請求
繞過頁面快取，否則等於白裝。

兩個相關細節：這類外掛的「熱門文章」查詢常靠 filter 掛排序，用 `get_posts()`
查要帶 `'suppress_filters' => false`（它預設會關掉 filter，排序條件悄悄失效）；
還沒有任何瀏覽紀錄時，熱門查詢回空集合是預期行為（多半是 INNER JOIN），
「熱門區塊沒東西」在累積出資料前不是壞掉。

### macOS AppleDouble

macOS 的 BSD `tar` 打包時，會把檔案的延伸屬性（extended attributes，例如 Finder
的標籤、來源資訊）額外包成一份隱藏的「影子檔案」，檔名是原檔名加上 `._` 前綴。
在 Linux 主機上解壓，這些影子檔案會變成一堆看起來莫名其妙的 `._*` 垃圾檔，混進部署
目錄裡。

**根治方法**：打包時加上環境變數 `COPYFILE_DISABLE=1`：

```bash
COPYFILE_DISABLE=1 tar czf archive.tgz -C <目錄> .
```

實測比對：不加這個變數，一次打包會夾帶近 20 個垃圾檔；加了之後是 0 個。這是
macOS 專屬的問題，在 Linux 上開發不會遇到，但只要你的開發機是 Mac，這一步就不能省。

### symlink 斷鏈

早期常見的本機開發做法是：把主題 repo 放在別的地方，再用 symlink 連到 WordPress
站台的 `wp-content/themes/` 底下。這個做法有兩個實測會炸的問題：

1. symlink 斷鏈（目標路徑改變、專案搬家）會讓 WordPress 找不到主題檔案，站台直接
   500 或路徑判斷全部錯亂。
2. 部分伺服器環境的 `realpath` 快取對 symlink 的行為不穩定，會讓「症狀時有時無」，
   排查起來比直接壞掉更難定位。

**正確做法：官方就地開發（in-place development）**——把 repo 本身直接設定成
WordPress 站台的主題資料夾，不透過 symlink 中介。這是 WordPress 官方建議的開發
方式，也是本起案包預設假設的環境結構。

### HTTP 200 不等於成功

`curl` 拿到 200 只代表「伺服器有回應內容」，不代表「回應的內容是你要的那個版本」。
快取住的舊版頁面、中繼架構的暫態攔截頁、還沒更新完成的部署，都可能回 200。

**判準是比對內容，不是看狀態碼。** 至少要抓一個「內容應該隨改動而變」的東西直接比對
（例如主題的 `style.css` 內容 md5、或頁面裡某段應該已經更新的文字），確認兩邊真的
一致。完整討論見 `docs/04-部署SOP.md` 最後一節。

### 顯示判斷分散兩處

「要不要顯示某個區塊 / 某段文字」這種條件判斷，如果在程式碼裡出現兩份各自獨立的
邏輯（例如桌機版一份、手機版另一份；或是模板檔一份、共用函式又一份），會製造出一個
很難查的坑：**本機因為有測試資料，兩份判斷剛好給出一致的結果，看起來完全正常；
正式站因為某個欄位還沒填值，兩份判斷的結果分歧，其中一份顯示、另一份不顯示**，
於是版面在正式站出現本機重現不出來的異常。

**規則：同一件事的「要不要顯示」判斷，全站只能有一份實作**，其他地方呼叫同一份，
不要各自重寫一次相近但不完全一樣的條件式。

### 回退值＝真實值

自訂欄位（ACF 或類似機制）常見的防呆設計是：欄位沒填值時，回退到一個看起來合理的
預設值，避免整個區塊開天窗。這個設計有一個隱藏的驗證盲點——**如果那個預設值剛好
跟「欄位確實接通並填了正確的值」長得一模一樣，你在前台看到正確的畫面，完全無法
分辨欄位系統到底有沒有真的接上**。

實測踩過兩次：一次在本機、一次在正式站，都是接欄位接完看前台顯示正常，事後才發現
其實整條路徑一路走的都是回退值，欄位系統從沒被真正呼叫過。

**判別方法**：
1. **清空欄位值再看一次**——如果清空後畫面完全沒變，代表你看到的原本就是回退值，
   不是欄位值。
2. **查資料庫**：確認欄位對應的值真的被存進去了，不是靠猜。
3. **臨時土法**：後台值後面手動加一個明顯的標記字串，前台如果出現那個標記，
   才確定讀到的是資料庫的值而不是回退值。這個方法快，但會短暫改到看得到的內容，
   測完記得改回來。

**正式站如果同時有頁面快取**，還會疊加一層假象：快取住的舊頁面也會讓你以為看到的
是最新狀態。分辨方法是比對快取檔案的產生時間跟你部署/填值的時間，快取時間早於
你的改動，代表你看到的就是舊快取，跟欄位系統有沒有接通無關。

### 硬編設計稿的分類清單

設計稿上常常會畫出一份分類清單（衛教文章分類、商品分類、標籤列表這類），乍看只是
排版用的靜態清單，直接把清單文字寫死進模板很省事——**但設計稿列的清單跟站上資料庫
裡真實存在的分類，經常對不上**。實測案例：設計稿列 12 個分類，站上實際有 18 個
子分類，其中只有 4 個名稱完全一致。

硬編清單造成的問題不是「看起來不對」而是**產生死連結**——清單裡有的分類，網站上
根本沒有對應的內容或連結目標，點下去是空頁或錯誤頁。

**規則：凡是設計稿畫出「一份清單」（分類、標籤、選單、地區、任何來自後台可管理資料
的列表），一律讀 WordPress 資料庫的真實資料生成，不要照畫面文字硬編。** 兩者對不上
時，把差異當成「內容管理該調整的事」回報給客戶或內容負責人，不要用硬編掩蓋過去。
讀真實資料的清單，未來後台調整分類時網站自動跟著對，不需要再改一次程式碼。

同一個道理也適用於「欄數固定寫死」——例如分類 tab 按鈕的欄數，設計稿畫的是固定
6 欄，但真實分類數量是由後台決定的變數，用能自動撐開/縮小欄數的排版方式（例如
CSS Grid 的 `auto-fit`）取代寫死的固定欄數，才不會在分類數量改變時版面跟著壞掉。

### 頁面建構器吞掉 header/footer

從舊的頁面建構器（Elementor、Divi 這類，常搭配它們自己的 Theme Builder 功能）遷移
到自刻主題時，最容易踩、代價也最高的一個坑：**只要頁面建構器的 Theme Builder 功能
還在啟用，即使你已經把某個頁面的內容換成自刻主題的版面，這個頁面的 header 與 footer
仍然可能被頁面建構器接管、蓋掉主題自己的版本**。

**機制**：頁面建構器的 Theme Builder 用 output buffering 攔截 WordPress 的
`get_header()` / `get_footer()` action，改印它自己指定的範本；如果沒有對應範本，
就什麼都不印——這解釋了為什麼 header 會「憑空消失」而不是「顯示成別的樣子」。
症狀特徵：`wp_body_open()` 這類鉤點有正常執行（追蹤碼出得來），但主題自己的
`<header>` 標籤完全不出現在渲染結果裡。

**正確順序（硬依賴，不能顛倒）**：

```
其餘頁面遷移完 → 才能停用頁面建構器 → header/footer 才會是自刻主題的
```

只要還有頁面依賴頁面建構器渲染內容，現在停用它會讓那些頁面全部塌掉。**先把其餘
頁面遷移完，最後才處理頭尾**，這條踩過一次代價很高（一次遷移的頁面數以個位數計，
一次性停用會讓所有頁面同時故障），不要為了「先把頭尾修好看」而提前停用。

**進階繞法**：如果暫時不想／不能停用頁面建構器，但想讓某個特定頁面（例如已經
遷移完成的首頁）先套用自刻主題的頭尾，可以繞過頁面建構器攔截的那兩個 action——
新增一個範本檔案，直接用 PHP 的 `require` 載入 `header.php` / `footer.php` 的內容，
**不呼叫** `get_header()` / `get_footer()`，那兩個 action 就不會被觸發，頁面建構器
自然不會介入。這個做法讓單一頁面提前繞過劫持，不必等到整站遷移完、也不影響其他
還在依賴頁面建構器的頁面。全站遷移完、正式停用頁面建構器之後，這個繞道範本可以刪除，
改回一般的 `get_header()` / `get_footer()` 呼叫。

## 第二節：驗證的紀律

**共同主題一句話：這裡每一條的失敗，看起來都跟成功一模一樣。**

第一節的坑，出事的時候多半有某種可觀察的異常（畫面壞了、連不上、檔案不見）。
這一節的坑不一樣——**驗證跑完顯示通過，但實際上該測的東西根本沒被測到**，這種
失敗不會主動告訴你哪裡不對，只會安靜地放行一個有問題的結果。

### 切版完成的定義：頁面對 ≠ 完成

實例：某個頁面早就切版完成、上線，頁面本身完全正確——但它的 footer 連結卻一直
指向 `#`（佔位符，從未接上真正的網址）。這個問題存在了很長一段時間都沒被發現，
即使這個頁面通過了每一項既有的驗收：PHP 語法檢查（`php -l`）過、六種寬度的版面
量測全部 PASS、`curl` 回 HTTP 200。

**但站上沒有任何一個地方連得到這個頁面。**

根因：所有既有的驗收項目問的都是「這一頁本身對不對」（語法對不對、版面對不對、
伺服器有沒有回應），沒有一項驗收在問「**站台走得到這一頁嗎**」——也就是「使用者
從首頁、從選單、從任何一個入口，實際點得到這個頁面嗎」。頁面本身完美無瑕，
但它是一座孤島。

**推論**：驗收清單不能只驗證「產出物本身」，還要驗證「產出物跟系統其他部分的連結
關係」。切一個新頁面，除了頁面本身要過檢查，還要確認至少有一條使用者能實際走到
的路徑（選單項目、內頁連結、麵包屑）指向它，缺了這一項，頁面做得再完美也等於不存在。

### 量測回報通過 ≠ 通過

自動化的版面寬度量測（例如檢查頁面在六種標準寬度下有沒有產生水平捲軸）全部回報
PASS，但實際上版面有問題，至少發生過兩種模式：

1. **元素級溢出**：整個頁面的捲動寬度沒有超標，但頁面裡某個特定元素自己超出容器、
   視覺上明顯跑版。量測工具通常用整個文件的 `scrollWidth` 判斷有沒有水平捲軸，
   這個判準測不到「元素被裁切或框架吸收了溢出，但視覺上仍然有問題」的情況（例如
   父層容器設定了 `overflow` 裁切，子元素撐出的部分被悄悄吃掉、量不到捲軸，
   但畫面上內容看起來就是被硬生生切斷）。
2. **整段內容漏放**：模板裡漏掉一整段應該出現的內容（例如漏掉一個 `<p>` 標籤包住的
   提示文字），這種缺漏**既不會讓頁面變寬，也不會讓 `scrollWidth` 對不上**——
   量測工具檢查的是「有沒有水平捲動」，跟「內容對不對、齊不齊全」是兩件完全不同的事。

**推論**：量測工具只管「有沒有水平捲動」這一件事，不管「內容對不對」。內容是否
完整、正確，只能拿實作結果跟設計稿做截圖比對，逐區塊核對，沒有替代的自動化捷徑。
兩種驗證方式要一起用，缺一種都會漏掉另一種能抓到的問題類型。

### 「數字串出現幾次」的檢查會失準

驗收「這段程式碼有沒有重用既有元件、不是重新切了一份」，直覺的做法是用
`grep -c` 之類的指令，去數某個元件名稱的字串在呼叫端程式碼裡出現了幾次。

**這個檢查隱含一個假設**：重用的痕跡會以「字面字串」的形式出現在被檢查的程式碼裡。
但如果實際寫法是用迴圈動態組出要 include 的檔名（例如把一組識別字放進陣列，
`foreach` 迴圈裡動態組字串去 `include`），元件的名稱字面上只出現在**被引入的那個
檔案本體**裡，不會出現在呼叫端的原始碼字面上——這種寫法下，`grep` 對呼叫端的
命中次數是 **0**，但實際上重用確實發生了。

**0 次不代表沒重用，代表 grep 挑的字串跟這段程式碼的抽象層級不對。**

**通則：任何「數某個字串出現幾次」的驗收檢查，先確認寫法本身會不會讓那個字串
以字面形式出現。** 動態組字串（變數、迴圈、字串格式化函式）幾乎必然會讓這類
`grep` 檢查失準——遇到這種寫法，要驗證重用有沒有發生，得追進被引入的那個檔案
本體去找函式名、class 名，並確認那個檔案在這次改動期間沒有被複製出另一份、
內容真的沒變過（改過就是掛羊頭賣狗肉的假重用；沒改過才是真重用）。

### 行號引用會漂移

跨 session、跨 agent 交接工作時，如果指位置只用行號（「看 `xxx.php` 第 230 行」），
一旦上游檔案在那之前被任何人編輯過、增減了幾行，**行號會整組錯位**，指到完全不同
的內容，而且不會有任何錯誤訊息告訴你指錯了。

**基本對策**：改用 class 名、函式名、註解裡的關鍵字，或用 `grep` 得到的具體字串
當定位依據，行號只能當輔助參考，不能單獨依賴。

**續篇，也是更重要的一條**：光是「改用 class 名定位」解決不了全部問題，真正的
問題不是「行號會漂移」，而是「**檢查範圍圈太小**」。實際發生過的情況是：一次改動
讓某個檔案整體增加了幾十行，導致該檔案後半段所有既有的行號引用（分散在另一份
文件裡，引用這個檔案很多處具體位置）全部同時失效。派工時如果只交代「驗證你新增
的引用」，執行者會忠實地把新增的引用都驗過、都是對的——**但舊引用完全不在任何人
的檢查範圍內，於是沒有人發現整份引用文件已經過期**。其中还有部分是「裸行號」
（只寫數字，沒有帶檔名前綴），連用正則去掃都掃不到，只能逐段閱讀才發現。

**通則：凡是改動了「被其他文件用行號引用」的檔案，要核對的是那份文件裡全部的
引用，不是只核對這次改動新增或碰過的部分。** 把檢查範圍限定在「自己的改動」，
對「自己的改動害別人的引用失效」這個方向是完全盲目的。

### 早退分支要留可分辨的 log

開發過程中常見一種難以定位的症狀：「頁面看起來沒套到樣式，但沒有任何地方會告訴你
為什麼」。程式邏輯裡如果有多個提前返回、提前跳出的分支（某個條件不滿足就直接
`return`、不繼續往下執行），而這些分支彼此之間、跟正常執行路徑之間，輸出看起來
可能一樣「沒有東西顯示」，排查時完全無從分辨到底是走了哪一條路才停下來。

**規則：開發環境下，每一個提前返回的分支都要各自寫一行可分辨的訊息**（可以是
`error_log`，也可以是任何開發環境才會啟用的除錯輸出），讓排查者一看就知道「這次
是在哪個判斷點被擋下來的」，而不是要逐一在程式碼裡插斷點才能分辨。

> **適用範圍**：這條講的是「同一個症狀可能來自好幾個不同判斷點」時，除錯用的
> log 該怎麼寫——多個早退分支彼此無法區分才需要這條。**不適用於**
> `docs/01-切版SOP.md`「沒資料就 `return`，整區不輸出」那種版型 partial：
> 那類早退只有一種「沒資料」的原因、輸出也刻意設計成「什麼都不印」，加 log
> 反而會在正式環境噴出雜訊。示範 partial（`template-parts/section-hero.php`、
> `template-parts/section-cards-3col.php`）維持裸 `return` 是刻意的，不是漏做。

### 白名單過嚴會安靜擋掉合法輸入

驗證或過濾機制如果用白名單（只允許清單裡列出的字元、格式、名稱），白名單本身
如果漏考慮了一種合法情況（例如漏掉底線這種常見的合法字元），會產生「合法輸入
被悄悄擋掉，沒有任何錯誤訊息」的結果——檔名被拒絕、CSS 悄悄沒被掛上，表面上
系統運作正常（沒有跳錯誤），但預期的行為就是沒有發生。

這類坑特別難查，因為**沒有失敗訊息可以追蹤**，唯一的線索是「預期該發生的事沒有
發生」。寫白名單機制時，先列出所有合法輸入的實際樣式，逐一核對白名單真的涵蓋，
不要憑印象覺得「應該夠了」。

### 煙霧測試標記漏掛是安靜的

用某個 class 名稱或標記字串是否出現，當作簡易的煙霧測試（smoke test）去驗證
某個功能有沒有生效，是常見的低成本驗收手段。但如果程式改動時漏掉了把這個標記
掛上去的那一步，**煙霧測試不會讓頁面壞掉，只會讓計數悄悄從某個數字變成 0**——
頁面外觀可能完全正常，只是少了那個原本該存在的標記。如果沒有人盯著這個計數本身，
這種漏掛可以在系統裡潛伏很久都不被發現。

### 這次做起案包時踩到的五個假檢查

把上面的通則具體化：以下是實際建這個起案包過程中，親身踩到的五個「檢查沒報錯，
但檢查本身失效了」的案例，全部來自 macOS 的 BSD 工具鏈跟 GNU 工具鏈的行為差異
（或工具被包裝過導致行為不穩定）：

| 工具／做法 | 問題 | 改用 |
|---|---|---|
| `awk`（macOS 內建是 one true awk） | `{n,m}` 這種數量詞、`\b` 這種詞界符號都**不支援，而且不會報錯**，正則悄悄退化成別的意思 | 改用逐位元展開的 pattern（把 `{n,m}` 展開成對應個數的重複寫法） |
| `sed`（macOS 內建是 BSD sed） | `\b` 不支援，同樣不報錯 | 改用 `[[:<:]]` / `[[:>:]]`（BSD 的詞界寫法） |
| `grep`（這台機器的 `grep` 是被包裝過的 shell 函式） | 當它是管線的第二段（接在別的指令後面）時，行為不穩定 | 過濾用途的那一段一律寫 `command grep`，繞過包裝直接呼叫真正的 grep |
| 用 `global $menu` 檢查 ACF 設定頁選單有沒有註冊 | 在 wp-cli（命令列）環境下執行時，這個全域變數永遠是空的——不是設定頁沒註冊，是**檢查的方式本身在這個執行環境下量不到東西** | 改用 `acf_get_options_pages()` 這個 ACF 提供的函式呼叫，不依賴只有網頁請求週期才會被填值的全域變數 |
| `grep -c 'commit'` 檢查某份文件有沒有記到一個 commit hash | 那一行文字裡字面上本來就寫著「commit」這個詞（例如「這裡要記 commit hash」這句提示文字本身），檢查**永遠回傳至少 1**，不管有沒有真的填上 hash | 改成驗證後面接的字串符不符合十六進位雜湊值的格式，而不是只數關鍵字出現次數 |

另外再加一條相關但獨立的教訓：**底線（`_`）在 POSIX 正則裡算是「詞字元」的一部分**，
所以拿詞界（word boundary）去比對像 `field_st_x` 這種變數名裡的 `st_`，抓不到——
因為 `_` 跟 `s`、`t` 一樣都算詞字元，`st_` 前後沒有真正的詞界。**這不是 BSD 工具鏈
獨有的行為，換成 GNU sed 一樣抓不到**，因為這是 POSIX 正則對「詞字元」的定義本身
造成的，不是哪個工具實作得不好。要抓這種帶底線的識別字片段，得直接寫出完整的替換
pattern（例如 `s/_舊前綴_/_新前綴_/g`），不要依賴詞界符號。

**這五個案例共同的教訓**：**寫完一個檢查，先故意製造它應該要抓到的錯誤情況，
確認它真的會回報失敗，再拿去驗真正的東西。** 上面每一個案例，如果當初有做過這一步
負向測試，都能在第一時間發現檢查本身失效，不必等到後來才發現「原來一直都沒真的
測到東西」。

> 任何驗證工具，用它之前先想一次「它失敗的時候會長什麼樣子」。
> 如果答案是「跟成功一樣」，它就不能單獨當作通過的依據。

### 負向測試的探針，要放在「真實內容會出現的位置」

「先故意製造它該抓到的錯」這條紀律，本身也有一種會失效的方式：**探針放錯位置**。

實案：驗證一支「頁面寬度量測工具」有沒有效，把一個 1800px 寬的探針元素插進頁面、
工具回報抓到了，於是宣告「工具有效」——但探針被插在頁面最外層，而**真實內容全都
包在一個 `overflow-x: clip` 的容器裡面**，容器裡的溢出被 clip 吃掉、`scrollWidth`
完全反映不出來。也就是說：工具只測得到「容器外面」的溢出，而真實內容永遠在
容器裡面——負向測試驗到的是一個**不會發生的情境**，工具對真正會發生的失敗
其實是瞎的。

**負向測試要模擬真實的失敗**：探針放進真實內容所在的容器裡、用實際會出現的
寫法去觸發，然後才看檢查有沒有抓到。探針在「不會有內容的位置」被抓到，
不構成任何證明。

順帶記一條走不通的修法：想消「有祖先在裁切」造成的量測假陽性，**不要用
「有祖先在裁切就自動排除該元素」**這條規則——當那個裁切容器本身就是全頁內容的
共同祖先時，這條規則會把每一個元素（連探針）都排除掉，等於永遠回報通過。

## 第三節：多人／多 agent 平行作業

這節現有的任何文件都沒寫過，但只要專案不只一個人（或一個 agent）在同時動，
遲早會遇到這裡列的情況。

### 平行化會放大規範缺漏的代價

兩個互不知情的 agent 各自獨立寫出「同一種沒有防護的寫法」，各自踩到同一個坑——
不是巧合，而是因為那條防護規則**存在於程式碼庫既有的其他元件裡，卻不存在於任何
文件**。單一 agent 循序做事，這類坑最多踩一次（踩到之後學到教訓，後面不會再犯）；
但兩個 agent 同時平行做同一類任務，同一個缺漏會被**平行踩兩次**——因為兩邊都沒有
機會從對方的經驗裡學到東西，各自獨立重蹈覆轍。

**反證也成立**：把這類教訓明確寫進派工封包（brief）之後，下一輪平行作業裡，
其中一份工作**一次通過、零 Critical 問題**——規則存在於文件裡跟存在於程式碼裡，
對「會不會被平行踩兩次」有實質差異。

**推論**：任何只存在於「資深工程師腦中」或「散落在某個元件實作細節裡」的防護規則，
一旦要開始平行派工，第一件事就是把它寫進共用的規範文件，不要假設每個 agent 都會
自己從既有程式碼裡歸納出同一條規則。

### 派工單寫的「已知結構」準確率很低

實測過三個 agent 平行接派工單，**全部都修正了控制端寫的「已知結構」描述**：
漏掉整個應該存在的區塊、把某種圖表類型寫錯成另一種、區塊的先後順序寫反。
最嚴重的一次是：派工封包聲稱某個檔案裡有一段可以參考的既有實作，執行的 agent
讀完整份檔案（數百行）之後才確認——**那段實作根本不存在，它只出現在設計稿裡**，
從未被真的寫進程式碼。

根源通常是：控制端撰寫派工封包時，對「已知結構」的描述其實來自對設計工具（例如
設計稿檔案的節點結構、座標）的**推斷**，不是對程式碼本身的**確認**。設計稿裡的
節點名稱如果是自動產生的流水號（沒有語意的命名），推斷出來的結構描述本質上是猜測，
猜錯的機率不低。

**規則：派工單要標明清楚哪些描述是「親眼確認過」（讀過程式碼、跑過指令驗證），
哪些是「推斷」（從設計稿節點、命名慣例、間接證據猜出來的）。** 引用任何「既有實作
可以參考」之類的說法之前，先確認那個實作真的存在，不要假設封包寫的就是事實。
執行者收到派工單時，也應該對「已知結構」保持懷疑，發現跟實際不符要主動回報並修正，
不要因為封包這樣寫就照單全收。

### 拆檔是為了避開無聲覆寫

多個 agent（或多個人）同時對同一個大檔案做追加式修改，會發生一種特別隱蔽的失敗
模式：**寫入回報成功，但內容被另一個幾乎同時發生的寫入覆蓋掉**——因為兩邊都是
基於「寫入前讀到的舊版本」去組出新內容再整份寫回，後寫入的那次會把先寫入的那次
覆蓋掉，兩邊都不會收到任何錯誤或警告。

**規則**：拆分工作範圍時，讓每個 agent 各自負責獨立的檔案，彼此不重疊（例如
「一頁一檔」，各頁各自的模板檔與樣式檔互不相干）。真的需要共用的入口（例如一份
彙整所有頁面連結的清單檔），改由**單一序列**維護——同一時間只有一個寫入者，
不讓多個平行的寫入者同時競爭同一份檔案。

### 三條實測有效的平行規則

實際跑過多輪平行派工（agent 數從 2 增加到 3，沒有出現新的衝突類型），歸納出三條
確實有效、可以直接沿用的規則：

1. **agent 不碰 git。** 多個 agent 同時執行 git 操作，`.git/index.lock` 會互相
   衝突。改由控制端在每個 agent 各自回報完成之後，**分別各自 commit**——git 操作
   全程只有控制端在跑，避免多個行程同時碰同一個 git 倉庫的鎖檔。
2. **除錯用的連線埠（例如瀏覽器自動化的 CDP port）要分流。** 不同 agent、以及控制端
   自己的驗證流程，各自用不同的埠號（例如慣例上一個埠給 subagent 用、另一個埠留給
   控制端）。不分流的話，後啟動的那一方發出的導航指令會把前一個還在使用中的頁面
   導航掉，兩邊互相干擾彼此的驗證結果。
3. **素材檔名前綴分流。** 每個 agent 負責的範圍各自用不同的檔名前綴（例如依頁面或
   模組命名），避免同時上傳/產生素材時互相覆蓋或搞混。實測過 31 個檔案、三種前綴
   全部零撞名。

這三條規則在 agent 數量增加時沒有暴露出新的衝突類型——代表它們解決的是平行作業
本身結構性的競爭問題（版控鎖檔、網路埠佔用、檔名空間），跟平行的規模無關，是可以
直接沿用的基礎規則，不需要每次增加 agent 數量都重新設計一套新機制。

### 多條工作線同時動同一個 repo 是常態，不是例外

上面講的是「一個控制端派多個 agent」；這條講的是另一種更隱蔽的並行——**多個
互不知情的工作階段**（不同的人、不同的 session、不同的電腦）同時在動同一個
repo。實測發現同一天同一個 repo 上有三條線同時在跑，彼此都不知道對方存在；
連兩條線互相通知時，**雙方都誤判了對方是誰**——A 以為某批 commit 是 B 做的、
B 查了 git log 才發現不是自己。

實測歸納的紀律：

- **判斷某個 commit 是誰做的，查 `git log --format='%an %ae'`，不要憑印象。**
- **對方宣稱「已完成」的工作，驗證實際狀態再依賴它。** 實測過文件註解寫
  「兩個區塊都接好了」，但其中一區的 markup 根本沒改——靠前台渲染結果逐一
  數元素才抓到。文件說做了不等於程式碼真的改了。
- **改動 commit hash 的操作（amend、rebase）要主動告知其他線**，否則對方的
  紀錄會指向一個不存在的 commit。
- **風險最高的交會點是部署**：鏡像部署會把「本機清單沒有的遠端檔」刪掉，
  兩條線在不同的 `main` 狀態下各自部署，後部署的會把前一條的東西當成遠端多餘
  而刪掉。完整紀律見 `docs/04-部署SOP.md`「多條工作線並行」一節。
