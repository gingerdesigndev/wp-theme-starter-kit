## 一、兩條公式：全站版面的唯一真相源

`style.css` §2 定義了兩條公式，這是這套起案包排版方式的核心，**逐字如下**：

```css
內容開版：width: min(var(--container), 100% - var(--gutter) * 2);
文章寬度：width: min(var(--measure),   100% - var(--gutter) * 2);
```

對應的 class 是 `.st-wrap`（內容開版）與 `.st-measure`（文章寬度）。

### 「內容開版」與「文章寬度」是兩個不同的東西

- **內容開版**（`--container`）：一般區塊／版面的寬度上限。首頁 Hero、卡片區、
  header、footer 這類「橫向鋪開」的區塊都用這條。
- **文章寬度**（`--measure`）：長文閱讀的行寬上限，通常比開版窄很多——這是排版
  常識：一行字太長會不好讀，所以內文區塊（單篇文章、頁面本文）要收得比整體版面
  更窄。

兩條公式的形狀完全一樣，差別只在用哪個 token 當上限（`--container` 還是
`--measure`）。`--gutter` 是兩條公式共用的安全邊界：不管上限多寬，畫面窄到連
`--container`／`--measure` 都放不下時，公式會自動改吃 `100% - var(--gutter) * 2`，
確保內容永遠離螢幕邊緣至少一個 `--gutter` 的距離。

### 換算示範（通用數字，不是任何客戶的實際值）

假設某個假想專案的 token 設定是：

- `--container: 1200px`
- `--measure: 640px`
- `--gutter: 24px`

在三個常見畫布寬度下，兩條公式各自算出來的實際寬度：

| 畫布寬度 | 內容開版：`min(1200, 畫布 − 48)` | 文章寬度：`min(640, 畫布 − 48)` |
|---|---|---|
| 375px（手機） | `min(1200, 327) = 327px` | `min(640, 327) = 327px` |
| 768px（平板） | `min(1200, 720) = 720px` | `min(640, 720) = 640px` |
| 1440px（桌機） | `min(1200, 1392) = 1200px` | `min(640, 1392) = 640px` |

看這張表可以觀察到兩件事：

1. **畫布越窄，兩條公式的結果越接近，甚至相等**（手機畫布下兩者都被
   `畫布 − gutter*2` 卡住，變成同一個數字）。畫布越寬，兩者的差距越明顯
   （桌機下開版是 1200，文章寬度只有 640）——這正是「文章寬度天生比開版窄」
   這個設計意圖在數字上的體現。
2. **表裡的每一格數字都是公式算出來的，沒有一個是手填的。** 拿到設計稿時，
   如果設計稿在某個畫布寬度下標示的版面寬度，正好是「這個畫布寬度 − gutter×2」
   或正好等於 `--container` / `--measure`，就代表這個設計稿是照這套公式邏輯
   畫的，可以直接把 `--container` 與 `--measure` 設成設計稿給的桌機數值，
   不需要另外為每個畫布寬度手動設定版面寬。如果設計稿標的數字對不上（既不是
   公式算出來的、也不等於任何 token），才需要回頭跟設計確認是否為個案例外
   （處理方式見第二節硬規則 4）。

**起案時要做的事**：拿到設計稿的桌機版面標值後，把 `--container` 設成設計稿的
「內容開版」寬、`--measure` 設成設計稿的「文章寬度」寬，`--gutter` 維持
出廠常數不要動（除非設計稿明確要求不同的留白值）。細節見第六節。

## 二、五條硬規則

這五條規則管的是「怎麼用這兩條公式」，不是公式本身。違反任何一條，會讓版面
出現兩個互相打架的寬度定義，通常的症狀是「明明改了 `--container` 卻沒用」
或「這個區塊的實際寬度量出來對不上任何 token」。逐字保留自 `style.css` §2
（class 命名已是這套起案包出廠時的 `.st-` 前綴，起案後 `起案.sh` 會自動把它
換成客戶專屬前綴，不需要手動改）：

1. **文字框不得超出開版寬，手機端不可貼齊螢幕邊緣。**
2. **滿版元素用 `100vw` 跳出容器是允許的，但其內部文字必須回到開版寬。**
   底色可以滿版，文字不行——這是兩件事，不要混為一談。
3. **不要用 `padding-inline` 造留白——留白由 `--gutter` 經公式產生。**
   額外再加 `padding-inline` 會讓「開版寬」同時被公式與 padding 兩邊定義，
   兩個定義通常會打架（疊加出比預期更窄的可視寬度），除錯時很難第一眼看出
   問題出在哪。
4. **區塊要收窄就覆寫 `--container`，不要另寫 `max-width`。**
   例：`.st-cards { --container: 1040px; }`。CSS 自訂屬性可以在任意選擇器上
   局部覆寫，覆寫之後這個區塊內所有吃 `.st-wrap` 公式的元素會自動跟著變窄，
   不需要另外找出所有相關元素個別加 `max-width`。
5. **不要為了排版反應去開新斷點——欄數變化用 `auto-fit` / `minmax()` 自己降欄。**
   例如卡片網格 `.st-cards__grid` 用
   `grid-template-columns: repeat(auto-fit, minmax(min(280px, 100%), 1fr));`，
   欄數會隨可用寬度自動增減，不需要為「窄螢幕變一欄、寬螢幕變三欄」這種需求
   額外寫 media query。`minmax()` 的下限務必包一層 `min(Xpx, 100%)`——如果寫成
   裸的 `minmax(280px, 1fr)`，畫布窄到連一欄 280px 都放不下時，軌道會被迫解析
   成固定 280px 寬，導致內容溢出可視範圍（而且因為 `.site-main` 設了
   `overflow-x: clip`，這種溢出既不能捲動、也不容易被截圖或量測工具發現）。

## 三、media query 白名單制度

**這套起案包的版面寬度規則不靠斷點（media query），只靠第一節的兩條公式。**
公式本身自帶「隨畫布寬度收縮」的能力，一般狀況下不需要為了版面寬度另外寫
`@media` 規則。

正因為公式已經處理了大部分情境，`style.css` §5 特別留了一張表，**當作 media
query 的白名單**：

```
| 斷點 | 管什麼 | 性質 |
|---|---|---|
| （目前無） |  |  |
```

出廠狀態這張表是空的——代表出廠時沒有任何情境需要開 media query。這不代表
永遠不能開，但**每加一條 media query，都要做兩件事**：

1. 在 `style.css` §5 的表裡登記：斷點數值、這條規則管什麼、為什麼需要它。
2. 在登記的說明裡，明確寫出「為什麼公式（或 `auto-fit`/`minmax()`）取代不了
   這條」——如果說明不出這一點，通常代表這個需求其實可以用第二節硬規則 5
   的 `auto-fit` 手法解決，不需要真的開 media query。

合理需要開 media query 的情境舉例（不是版面寬度，是**行為**變化）：某個元件在
窄螢幕下要整個換掉排列邏輯（例如桌機是水平 tab、手機要收成手風琴），這種
「結構性的行為切換」是公式管不到的，媒體查詢在這裡是合理工具。但如果只是
「欄數變化」「元素變窄變寬」這類**寬度**問題，先看能不能用第一、二節的公式
與 `auto-fit` 解決，不要直接跳去開新斷點。

## 四、字級系統（全專案通用標準，內嵌對照表與注意事項）

> 這一段的內容來源是 `~/.claude/skills/typography-scale/SKILL.md`（野薑設計內部
> 通用字級系統 skill）。**因為這份文件會被複製到每個客戶站的主題目錄裡、在不同
> 電腦上開發，而那支 skill 只存在維護者自己電腦的 `~/.claude/skills/`，別台電腦
> 讀不到它**，所以這裡把字級表與注意事項逐項抄錄進來，不用引用的。來源 skill
> 還有一節「怎麼在專案裡套用」（drop-in CSS 檔、Tailwind 設定）——**本專案手寫
> CSS，不使用那套 drop-in 檔案路徑**，所以那節故意省略，不是漏抄。
>
> **這一組是全專案通用標準，不要每站重訂。** 起案後除非設計稿明確要求例外
> （見本節最後一條注意事項），字級系統本身不在客製化範圍內。

以 `rem` 為單位（`1rem = 16px`，瀏覽器預設根字級）。字重：Bold = 700、
regular = 400。行高用無單位倍數。字距用 `em`（會隨字級縮放，比用 `%` 更可攜）。

| 元素 | 字級 | 字重 | 行高 | 字距 |
|---|---|---|---|---|
| H1 | 2.25rem（36px） | 700 Bold | 1.3（130%） | 0.1em（10%） |
| H2 | 1.75rem（28px） | 700 Bold | 1.3（130%） | 0.1em（10%） |
| H3 | 1.375rem（22px） | 700 Bold | 1.3（130%） | 0.1em（10%） |
| H4 | 1.25rem（20px） | 700 Bold | 1.5（150%） | 0.1em（10%） |
| H5 | 1.125rem（18px） | 700 Bold | 1.5（150%） | 0.1em（10%） |
| H6 | 1rem（16px） | 700 Bold | 1.85（185%） | 0.1em（10%） |
| p（內文） | 1rem（16px） | 400 regular | 2.0（200%） | 0.05em（5%） |
| small | 0.875rem（14px） | 400 regular | 1.85（185%） | 0.05em（5%） |

重點記法：**標題群（H1–H6）一律 Bold（700）、字距 10%（0.1em）**；
**內文群（p、small）一律 regular（400）、字距 5%（0.05em）**。行高則越往小級數、
越接近內文，行距越鬆，是刻意給閱讀留呼吸空間。

**注意事項（同樣抄自來源 skill）：**

- **rem 隨根字級縮放**：表中 px 是在 `html { font-size: 16px }`（瀏覽器預設）下的
  換算值。若專案改了根字級，rem 會整體等比縮放，階層比例仍然成立——這正是用
  rem 的好處，不要把表格數字改成寫死的 px。
- **字距用 em 不用 px**：`0.1em` 會跟著各級字自動放大縮小，維持視覺一致；若某
  專案硬性要求用 `%`，換算是 10% ≈ 0.1em、5% ≈ 0.05em。
- **要例外時先問**：若某個設計稿的標題明顯不在這八級內（例如超大 Hero 標題），
  跟提出需求的人確認是要新增一級、還是套最接近的既有級數，不要默默自己發明
  尺寸——這是全專案共用的表，隨意加尺寸會讓不同站之間的字級系統慢慢失去一致性。

## 五、`design-system.md` 同步紀律（硬性規則）

`design-system.md` 是**全站樣式的唯一真相源**：新接手的人（或 AI）要知道這個站
的顏色、間距、字體、版面規則長什麼樣，讀這份文件就夠，不需要去讀整支 `style.css`
反推。

這件事能成立的前提是：**文件內容必須跟程式碼實際狀態一致**。所以這是一條硬性
規則，不是建議——

> **改了 `style.css` 或 `functions.php` 裡任何跟樣式／內容欄位相關的東西，
> 就要同步更新 `design-system.md`。**

具體來說：

- **新增或修改顏色、間距 token** → 更新 `design-system.md` 的「顏色 Tokens」／
  「間距 Tokens」表，不要只改 `style.css` 就結束。
- **新增元件（新的 `.st-xxx` class 群、新的區塊樣式）** → 在「元件」章節補一節，
  說明這個元件是什麼、掛在哪個模板檔／pattern、用到哪些 token。
- **新增 media query** → 除了照第三節在 `style.css` §5 登記，也要同步反映在
  `design-system.md` 的 RWD 章節（如果那裡也維護了 media query 清單）。
- **暫時沒空寫完整說明的東西** → 記一條 TODO 到「待補 TODO」章節，**不要什麼都
  不寫**。空白的文件比寫了 TODO 的文件更危險：後者至少讓下一個人知道這裡還沒
  處理，前者會讓人誤以為「沒寫到的地方就是沒有」。

反過來說：**如果 `design-system.md` 寫的規則跟程式碼實際做法不一致，一律是
文件錯，不是程式碼錯。** 發現不一致時，先確認程式碼目前的行為才是「應該」的
行為（還是程式碼本身也需要修正），再回頭改文件對齊。不要憑印象、憑文件裡舊的
描述去改程式碼——這樣會把當初程式碼修正的理由一起改掉。

## 六、起案時 tokens 要做什麼

新站起案（跑完 `起案.sh` 之後）拿到設計稿，關於 `style.css` §1 tokens 的
待辦事項：

1. **換顏色**：把 `--color-main` / `--color-accent` / `--color-text` /
   `--color-muted` / `--color-bg` / `--color-bg-alt` / `--color-line` 這組
   中性佔位色，換成設計稿或品牌指南給的實際色碼。**不要在任何 CSS 或 PHP 裡
   直接寫死色碼**——所有顏色都應該透過這組 token 引用，之後要整站改色（例如
   品牌色微調）才能只改一個地方生效。換色後同步更新 `design-system.md` 的
   「顏色 Tokens」表。
2. **依設計稿調整 `--container` 與 `--measure`**：做法見第一節，把設計稿量到
   的「內容開版」桌機寬度設成 `--container`、「文章寬度」桌機寬度設成
   `--measure`。
3. **`--gutter` 建議維持出廠常數**（`20px`），除非設計稿明確要求不同的留白值。
   `--gutter` 是全站兩條公式共用的安全邊界，維持常數能確保「窄畫布下開版與
   文章寬度收斂成同一個值」這個行為在所有站之間一致，不需要每站重新驗證。
4. **字級系統維持出廠值，不要調整**（見第四節）——這是全專案通用標準，除非
   遇到設計稿明確要求的例外情況。
5. **字體家族**（`--font-sans` / `--font-serif`）換成設計稿指定的字族。

以上每一項改完，都要回頭在 `design-system.md` 對應章節填上實際值——這正是
第五節同步紀律要求的事，起案階段的 token 調整是最常漏掉同步文件的時間點，
因為當下的心力都在「讓畫面對得上設計稿」，容易忘記文件也要跟著更新。

## 七、WebKit 專屬的幾種寫法

這一節全部來自「iPhone 有、Mac Chrome 沒有」的實案。共同點：**Chromium 算出來是對的，
WebKit 把同一份 CSS 算成另一個結果**，而且沒有任何錯誤訊息。客戶端一定有 iPhone 用戶，
所以「Chromium 六寬度全 PASS」不代表 iOS 沒事。每一條改完都用
`node tools/webkit-overflow.mjs <url> --engine=both --widths=320,375,414` 量一次——
`--engine=both` 會把**只在 WebKit 出現**的溢出單獨列出來，那些就是這一節在講的東西。
工具用法見 `tools/_webkit-lib.mjs` 檔頭；它抓得到「引擎差異」，抓不到「舊版本差異」
（停在舊 iOS 的機器），後者還是要實機。

1. **版面 grid 的 `1fr` 要寫 `minmax(0, 1fr)`。** WebKit 算 `1fr`（＝`minmax(auto, 1fr)`）
   欄的最小寬時，會把欄內 `width:100%` 的圖片當成**原始尺寸**、再被側欄 `max-width`
   夾住，整欄撐成 420px、右邊破出視窗；Chromium 把這種循環百分比算 0。
   ⚠️ 這條跟另外兩處講的 `minmax` 是三件不同的事，不要混：第二節硬規則 5 的
   `minmax(min(280px,100%), 1fr)` 是**下限**不能寫死 px；`docs/05-踩坑清單.md` 輪播節的
   「`grid-auto-columns` 不要用 `minmax(0, X)`」是**輪播軌道**上下限為 0 會被壓縮。
   這裡是**版面欄**的 `1fr` 下限要明寫 0，三者各自成立。

2. **grid item 要「限寬＋置中」，寫 `width: min(Npx, 100%)`，不要只給 `max-width` 配
   `margin-inline: auto`。** auto 外距會讓 grid item 不再 stretch、寬度變 fit-content；
   WebKit 又把裡面 `width:100%` 圖片的最小寬算成原始尺寸，結果 `max-width:339px`
   在 375 手機上被撐成 339（容器只有 335）、320 寬直接破出視窗。改成 `width:min(339px,100%)`
   後 320／375／414 是 280／335／339。側欄、卡片要限寬置中一律用這個寫法。

3. **不用 `@container`／`container-type`。** iOS 16 的 iPhone 8 會把整張卡的寬度算成 0，
   兩欄塌成一字一行；新 iPhone 與 Mac 完全正常。客戶群裡有舊機時相容性優先於「不開斷點」——
   第二節硬規則 5 的精神是**不堆新斷點**，不是禁用既有的；要切換元素顯示或搬位置這種
   `clamp()`／`auto-fit` 做不到的事，直接用既有斷點，別為了守規則去碰新 CSS 功能。

4. **flex 子項帶 `overflow:hidden` 時最小尺寸是 0。** flex 直排裡內容高過容器，唯一帶
   `overflow:hidden` 的子項（例如要裁圓角的搜尋框）會被壓扁到只剩框線（實測 2px），
   其他沒 overflow 的子項不縮。要撐住的子項明寫 `flex-shrink: 0`；修在該元件的覆寫那一行，
   不動共用元件。兩引擎都一樣，不是 iOS 專屬，但症狀「搜尋框不見了」很難聯想到這裡。

5. **固定在視窗底的元素（快捷列）會蓋住任何 `inset: … 0` 的 fixed 容器內容。** 容器底部
   留白要寫成「底欄高 ＋ `env(safe-area-inset-bottom)` ＋ 間距」，不要寫一個巧合比底欄
   高一點的常數；兩處的數字用註解互指，改其中一個時另一個才會跟著改。有 Home 指示條的
   iPhone 底欄實際高度多 34px，模擬器量不到（見 `docs/05-踩坑清單.md` 第二節）。

6. **小目標用 `::before` 外擴熱區時，水平外擴不能超過縫隙的一半。** 圓心距 14px 的一排
   圓點外擴到 24px 寬，後一顆的熱區疊在前一顆的可視區上，`elementFromPoint` 在第 1 顆右半
   回第 2 顆——「加熱區讓手指點得到」反而讓點到的不是看到的那顆。寫法
   `inset: -10px calc(var(--gap) / -2 - 1px)`：`inset` 以 padding box 起算，要多扣 border；
   縫隙左右各半分，熱區相接不重疊。

7. **輪播／卡列：每頁張數是 CSS 變數，卡寬與位移全 CSS 算，JS 只翻頁。**
   變數掛在 JS 的 root 元素（`<section data-cardrow>`）——掛內層讀不到、每頁永遠 1。
   卡寬 `= (100% − gap × (n−1)) / n`，翻頁位移 `= 頁數 × (100% + gap)`，JS 只讀變數算頁數。
   手機一張 = 100% 寬天然置中，不用 JS 量塞幾張再算置中位移（舊做法的副作用是手機靠左
   露邊、桌機第二頁偏 47px）。每頁張數用**既有**斷點切，這是硬規則 5 的一個被裁定的例外。

8. **驗有動畫的元件，瀏覽器面板在背景時先注入 `* { transition: none !important }`。**
   面板不在前景時渲染被節流，CSS transition 停在起點、IntersectionObserver 不觸發，
   量輪播翻頁位移會連續讀到 identity——其實 CSS 沒錯。reveal 區塊也要先 `scrollIntoView`
   或直接看 class。量 transform／opacity 類的東西先排除時序，再懷疑 CSS。
