# 收工流程

當使用者表示要結束今天 / 這段工作時，跑這個流程。

**不跳選單、不先問。** 直接更新 `HANDOFF.md` 和 `MEMORY.md`（兩個都做），全部寫完後一次回報。

兩個檔案都放在**專案根目錄**（這個站的主題根目錄），不是使用者個人電腦上的全域設定路徑。
如果 cwd 顯然不是專案根，先問使用者要不要寫到別的位置，再繼續。

## 第一步：更新 HANDOFF.md

寫到**專案根目錄**的 `HANDOFF.md`（**整份覆蓋**，不累加）。第一行的
起案包 commit hash 是起案時寫入的錨點，覆蓋時保留那一行，不要刪掉。

格式：

```markdown
# HANDOFF — <站名>

> 起案自「WP 自刻主題起案包」commit `<hash，保留原值不要改>`。
> 這份記「這次做了什麼、下次怎麼接」；跨對話的長期事實寫 MEMORY.md，兩邊不要重複。

## 這次做了什麼
- ...（重點 3-6 條）

## 改動的檔案
- path/to/file.php — 改了什麼
- ...

## 還沒做完 / TODO
- ...（明確列出下次要接的事）

## 下次怎麼接
從 X 開始；先跑 `Y` 確認狀態；然後做 Z。
```

寫前先用 `git status` 或對話脈絡確認真的改了什麼，**不要憑印象寫**。

## 第二步：更新 MEMORY.md

寫到**專案根目錄**的 `MEMORY.md`（**累加**在最後，不覆蓋）。

如果檔案不存在，先建立（格式見 `MEMORY.template.md`）。

每筆新增格式：

```markdown
## <YYYY-MM-DD> <短標題>
<事實 / 慣例 / 偏好的描述>
```

只挑**值得跨對話記、而且只對這個客戶有意義**的寫進去：

- 一次性的事不寫
- 主機資訊、品牌 tokens、這個客戶的偏好、只在這個站踩過的坑才寫
- **通用的教訓**（換一個客戶站也用得上的踩坑或更好的做法）不要寫進 MEMORY.md，
  改寫進 `docs/回饋正本.md`——那份之後會由維護者人工回灌起案包正本，寫錯地方
  下一個站就學不到
- 這次若真的沒有值得記的長期事實，**就不要硬加**——MEMORY.md 維持原樣即可，
  並在回報時說明「這次沒有值得寫進 MEMORY 的長期事實」

## 第三步：回報

兩個檔案處理完後，一次回報，例如：

> 收工完成。
> - HANDOFF.md 已更新（路徑：./HANDOFF.md）
> - MEMORY.md 已新增 N 筆（或：這次沒有值得寫進 MEMORY 的長期事實）
> - 回饋正本.md：N 筆通用教訓（或：這次沒有對下一個站也有用的教訓）
> 下次見。

## 多個 session 同時在這個站工作時

先 `ListAgents` 看有沒有別的 session。有的話，**一天只有一個 session 跑這個流程**：

- 你是**審查 session**（負責 push／部署的那個）→ 照上面做，並把改碼 session 傳來的三段
  （做了什麼／留給使用者裁定的／學到的教訓）合併進去。
- 你是**改碼 session**（只 commit、不 push）→ **不要跑這個流程**。用 SendMessage 把那三段
  傳給審查 session，由它寫。審查 session 已經先收工的，用 Edit 對 `HANDOFF.md`／`MEMORY.md`
  **局部追加**，不要整份覆蓋、不要重跑。
- 不確定自己是哪一個 → 問使用者，不要兩邊都寫。

理由：HANDOFF.md 是整份覆蓋，兩個 session 各跑一次，後跑的會把先跑的蓋掉
（細則見 `docs/07-審查清單.md` 第八節）。

## 重要規則

- **HANDOFF.md = 單一檔案、每次覆蓋（commit hash 那一行例外，保留）**；
  **MEMORY.md = 累加，不覆蓋**。
- 兩個檔案都放在**專案根目錄**，不是使用者個人電腦上的全域設定路徑。
- 收工 = 直接動手，不要再跳選單問使用者要做哪個。
